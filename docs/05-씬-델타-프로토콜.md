## 0. 이 문서가 정하는 것

호스트 앱(SketchUp)에서 렌더러(IRIS)로 씬을 **처음 한 번 전부** 보내고, 이후 **바뀐 것만**
보내는 규약입니다.

[00-진행상황.md](00-진행상황.md) ②에서 확정한 대로, 지금은 SketchUp 하나만 붙이지만
**프로토콜은 SketchUp에 종속시키지 않습니다.** 나중에 axia-sketch·AXiA3D·IFC 임포터가
생산자로 합류할 때 재설계가 없어야 하기 때문입니다.

---

## 1. 왜 glTF로는 안 되는가 — 실측된 세 가지 + 하나

파이프라인 검증에는 glTF를 썼고 잘 동작했습니다([04번 문서 6·7절](04-RTXPT-실측.md)).
그러나 **라이브 링크에는 못 씁니다.**

| # | 막히는 것 | 실측 근거 |
|---|---|---|
| 1 | **재질 상속** | 메시 버킷의 **40%**(469중 188)가 재질 미지정. SketchUp은 상위 인스턴스 재질을 상속하는데, glTF는 메시를 공유하므로 인스턴스별 오버라이드를 표현할 수 없다. 메시를 재질별로 복제하면 **인스턴싱 이득(재사용률 4.00)이 사라진다** |
| 2 | **안정적 ID** | `persistent_id`를 실을 자리가 없다. 이게 없으면 델타 추적이 불가능하다 |
| 3 | **레이어(태그)** | 가시성 제어에 필요한데 실을 자리가 없다 |
| 4 | **크기·속도** | 골프존 모델(삼각형 400,062) 기준 **JSON 140.6 MB, 기록에만 7.6초**. 같은 데이터의 바이너리 환산은 **33.8 MB(4.2배 작음)**. 텍스트 파싱 비용은 별도 |

4번이 결정적입니다. **7.6초는 라이브 링크의 갱신 주기가 될 수 없습니다.**

## 2. 설계 원칙

1. **바이너리.** 지오메트리는 파싱 없이 GPU 업로드 가능한 형태로 보낸다
2. **호스트 비종속.** SketchUp 개념(`Sketchup::ComponentDefinition` 등)을 규약에 넣지 않는다
3. **정의/인스턴스 분리 유지.** 이것이 곧 BLAS/TLAS 구조다. 실측 재사용률 4.00(세종) /
   1.64(골프존) — 지오메트리 메모리가 그만큼 절약된다
4. **원본 좌표계 보존.** Z-up, 미터. 변환은 소비자 책임.
   역방향(렌더러 → 호스트) 경로를 나중에 열 때 쉬워진다
5. **멱등성.** 같은 델타를 두 번 받아도 결과가 같아야 한다. 재연결 시 복구가 단순해진다
6. **부분 실패 허용.** 텍스처 하나를 못 받아도 씬은 뜬다

## 3. 두 개의 채널

```
호스트 확장 (SketchUp 안)              IRIS 렌더러 (별도 프로세스)
  ┌──────────────────┐                  ┌──────────────────┐
  │ Ruby: 변경 감지   │──── 제어 ───────▶│ 메시지 처리       │
  │ C++: 지오메트리   │                  │                  │
  │      추출         │──── 벌크 ───────▶│ BLAS/TLAS 구축   │
  └──────────────────┘                  └──────────────────┘
```

| 채널 | 용도 | 특성 |
|---|---|---|
| **제어** | 메시지 헤더, 인스턴스 변환, 삭제 통지, 카메라, 명령 | 작고 잦음. 순서 보장 필요 |
| **벌크** | 정점·인덱스 버퍼, 텍스처 이미지 | 크고 드묾. 순서 무관, 참조로 연결 |

제어는 작아서(인스턴스 하나가 수십 바이트) 소켓으로 충분합니다. 벌크는 골프존 기준
33.8 MB이므로 **공유 메모리**가 유리합니다.

> **미결정 A**: 벌크를 공유 메모리로 할지 소켓으로 할지. C API 추출 속도를 재봐야
> 결정할 수 있습니다 — 추출이 병목이면 전송 방식 차이가 묻힙니다.

## 4. 데이터 모델

### 4.1 식별자

| 종류 | 값 | 비고 |
|---|---|---|
| `DefId` | u64 | 정의(재사용 가능한 지오메트리)의 안정적 ID |
| `InstId` | u64 | 인스턴스의 안정적 ID. SketchUp에서는 `persistent_id` |
| `MatId` | u64 | 머티리얼 |
| `TexId` | **콘텐츠 해시** (u128) | 이미지 내용의 해시. 같은 이미지를 두 번 보내지 않는다 |

`TexId`만 콘텐츠 주소를 쓰는 이유: 텍스처는 크고(골프존 40개), 모델을 다시 열어도
내용이 같으면 재전송할 필요가 없습니다. 렌더러가 캐시로 들고 있으면 됩니다.

> ⚠ **삭제 시 ID 매핑은 호스트 확장의 책임입니다.** SketchUp의 `onElementRemoved`
> 콜백은 **`entityID`(세션 한정 정수)만** 주고 `persistent_id`를 주지 않습니다
> ([과제 4 실측](../tools/sketchup/README.md)). 확장이 `entityID → InstId` 표를
> 유지해야 하며, 프로토콜에는 **항상 `InstId`만** 실립니다.

### 4.2 정의 (Definition)

```
Definition {
  id:        DefId
  name:      string          // 디버깅용. 의미 없음
  meshes:    [MeshBucket]    // 재질별로 나뉜 지오메트리
  children:  [ChildRef]      // 중첩 인스턴스
}

MeshBucket {
  material:  MatId?          // 없으면 상속 (5절)
  vertices:  BufferRef       // position3 + normal3 + uv2, f32 interleaved
  indices:   BufferRef       // u32
  count:     { verts: u32, tris: u32 }
}

ChildRef {
  id:        InstId
  definition: DefId
  transform: [f64; 16]       // 열 우선, 평행이동은 미터
  material:  MatId?          // 인스턴스 재질 오버라이드 (5절)
  layer:     LayerId?
  flags:     { hidden: bool }
}
```

정의는 **한 번만** 보내고 인스턴스가 참조합니다. 이것이 BLAS 재사용입니다.

### 4.3 머티리얼

```
Material {
  id:        MatId
  name:      string
  base_color: [f32; 3]       // 선형
  alpha:     f32
  texture:   TexId?
  // 확장 여지: roughness, metallic, normal map, emissive
}
```

> **미결정 B**: PBR 파라미터를 어디까지 실을지. SketchUp은 색·알파·텍스처만 주므로
> 나머지는 렌더러가 추정하거나 사용자가 지정해야 합니다. 재질 편집 UI 설계와 함께
> 정해야 합니다.

### 4.4 뷰

```
View {
  name:      string
  eye:       [f64; 3]        // 미터, Z-up
  target:    [f64; 3]
  up:        [f64; 3]
  fov_deg:   f32
  perspective: bool
}
```

실측: 세종 28개(전부 외부 조감), 골프존 4개(전부 눈높이 1.2~1.4 m).
**설계자가 잡아둔 시점이므로 제품에서 그대로 노출해야 합니다.**

### 4.5 조명 — 호스트가 주지 않습니다

⚠ **SketchUp에는 광원 엔티티가 없습니다.** 태양과 앰비언트뿐이며, 실측에서 골프존의
천장 스포트라이트는 전부 지오메트리였고 렌더러가 본 광원은 **환경광 1개**였습니다.

따라서 조명은 **프로토콜이 호스트에서 받아오는 것이 아니라 IRIS가 자체적으로 갖는
상태**입니다. 프로토콜에는 다음만 실립니다.

```
SunState  { azimuth, altitude, date_time, ... }   // 호스트가 주는 것
```

나머지(인공조명 배치·강도·색)는 IRIS 쪽 UI와 저장소가 담당합니다.
**Enscape이 자체 조명 UI를 제공하는 이유가 이것입니다.**

## 5. 재질 상속 — glTF가 못 하는 것을 렌더러는 할 수 있습니다

문제: SketchUp에서 면에 재질이 없으면 **상위 인스턴스의 재질**을 씁니다.
같은 정의가 두 인스턴스에서 다른 색으로 보일 수 있습니다.

glTF가 못 하는 이유: 메시가 인스턴스 간 공유되므로 재질을 메시에 박아야 하고,
인스턴스별로 다르게 하려면 메시를 복제해야 합니다 → 인스턴싱 이득 소멸.

**해결: 레이트레이서의 인스턴스 데이터를 쓴다.**

DXR/Vulkan의 TLAS 인스턴스는 각각 **24비트 사용자 인덱스**(`InstanceID` /
`instanceCustomIndex`)를 가집니다. 히트 셰이더에서 이 값을 읽어 인스턴스별 테이블을
조회할 수 있습니다.

```
프로토콜:  MeshBucket.material = null  → "상속"
           ChildRef.material   = MatId → "이 인스턴스는 이걸로"

렌더러:    TLAS 인스턴스마다 custom index = 인스턴스 슬롯 번호
           히트 시  material = bucket.material ?? instance_table[idx].material
                             ?? default_material
```

지오메트리는 **한 벌만** 유지하면서 인스턴스마다 다른 재질이 나옵니다.

> **이것이 자체 프로토콜의 첫 번째 실질적 이득입니다.** 제약은 glTF의 것이었지
> 레이트레이서의 것이 아니었습니다.

상속 해석 순서는 **소비자(렌더러)가** 수행합니다. 호스트 확장이 미리 풀어서 보내면
정의를 복제하게 되므로 그렇게 하지 않습니다.

## 6. 델타 의미론

### 6.1 메시지

| 메시지 | 방향 | 내용 |
|---|---|---|
| `Hello` | 양방향 | 버전, 능력 협상 |
| `SyncBegin` / `SyncEnd` | 호스트→렌더러 | 전체 동기화 경계 |
| `DefUpsert` | 호스트→렌더러 | 정의 추가/갱신 (지오메트리 포함) |
| `DefRemove` | 호스트→렌더러 | `DefId` |
| `InstUpsert` | 호스트→렌더러 | 인스턴스 추가/갱신 (변환·재질·레이어) |
| `InstRemove` | 호스트→렌더러 | `InstId` |
| `MatUpsert` / `MatRemove` | 호스트→렌더러 | |
| `TexUpsert` | 호스트→렌더러 | `TexId` + 이미지 바이트. 렌더러가 이미 가지면 생략 |
| `ViewSet` | 호스트→렌더러 | 저장 시점 목록 |
| `SunSet` | 호스트→렌더러 | 태양 위치 |
| `CameraSync` | 양방향 | 현재 뷰포트 카메라 (선택) |
| `TexQuery` | 렌더러→호스트 | "이 `TexId` 갖고 있나" — 재전송 회피 |

`Upsert` 하나로 추가와 갱신을 겸합니다. 멱등성(원칙 5)이 여기서 나옵니다.

### 6.2 트랜잭션 경계

SketchUp의 `ModelObserver#onTransactionCommit`이 편집 단위를 알려줍니다
([과제 4에서 확인](../tools/sketchup/README.md)). **커밋 단위로 델타를 묶어 보냅니다** —
드래그 중 매 프레임 보내면 BLAS 재구축이 폭주합니다.

```
onTransactionStart  →  델타 수집 시작
  (편집 이벤트들)
onTransactionCommit →  묶어서 전송
```

### 6.3 지오메트리가 바뀌면

정의의 지오메트리가 바뀌면 `DefUpsert`로 **정의 전체**를 다시 보냅니다.
부분 갱신은 하지 않습니다 — BLAS는 어차피 재구축해야 하고, 부분 갱신 로직의
복잡도가 이득보다 큽니다.

### 6.4 델타 비용 — 정의 크기 분포

"정의 하나가 바뀌면 얼마를 다시 추출해야 하는가"는 정의 크기 분포로 답이 나옵니다.
골프존 모델(정의 706 / 삼각형 400,062) 실측:

| 분위 | 삼각형 | 전체 대비 | 재추출 시간 |
|---|---|---|---|
| 중앙값 | 20 | 0.00% | **0.6 ms** |
| 75% | 160 | 0.04% | 5.1 ms |
| 90% | 822 | 0.21% | **26.0 ms** |
| 99% | 14,112 | 3.53% | **446 ms** |
| 최대 | 35,791 | 8.95% | **1,131 ms** |

(재추출 시간은 캐시 없는 실측 속도 31,637 tri/s 기준)

- **지오메트리가 없는 정의가 277개(39%)** 입니다. 순수 컨테이너이며 재추출 비용이 0입니다
- **상위 5개 정의가 전체 삼각형의 31.4%** 를 차지합니다

#### 7절의 50 ms 목표에 대한 답

**편집의 90%는 26 ms 이내에 반영됩니다.** 목표 안입니다.

문제는 상위 1%입니다 — 14,112 삼각형짜리 정의를 건드리면 446 ms, 최대 정의는 1.1초가
걸립니다. **미결정 C가 실재하지만 범위는 좁습니다.**

대응 후보:

| 방안 | 비고 |
|---|---|
| 이전 버전을 계속 보여주며 백그라운드 재추출 | 50 ms 목표를 "반영 시작"이 아니라 "체감 지연 없음"으로 재정의 |
| 워커 스레드 추출 | C API 필요. Ruby는 메인 스레드에 묶인다 |
| 큰 정의 분할 | 복잡하고 인스턴싱 구조를 깨뜨린다. 마지막 수단 |

측정 도구: [`iris_probe.rb`](../tools/sketchup/iris_probe.rb)의 `dirty_report` —
편집 후 호출하면 무효화된 정의와 재추출 예상 비용을 보고합니다.

> **미결정 C** 는 위 분석으로 범위가 특정됐습니다(상위 1% 정의). 남은 것은 실제
> 편집이 어떤 정의를 얼마나 자주 건드리는지이며, `dirty_report` 로 잽니다.

## 7. 성능 목표 — 추출 병목의 실체

### 7.1 어디에 시간이 가는가 (실측)

[`tools/sketchup/iris_bench_extract.rb`](../tools/sketchup/iris_bench_extract.rb)로
골프존 모델의 면 30,000개(삼각형 약 51,433개)를 추출 방식별로 측정했습니다.

| 방식 | 초 | 삼각형/초 | A 대비 |
|---|---|---|---|
| **A 현재 프로브** (point_at/normal_at/uv_at + rescue) | 1.061 | 48,487 | 1.0배 |
| B rescue 제거 | 1.003 | 51,297 | 1.1배 |
| C + `points` 벌크 접근 | 1.014 | 50,707 | 1.0배 |
| D + 면 법선 사용 (정점 법선 포기) | 0.980 | 52,501 | 1.1배 |
| **E 위치+인덱스만** (법선·UV 없음) | 0.431 | 119,289 | **2.5배** |
| **F `mesh()` 호출만** (추출 없음) | 0.094 | 547,004 | **11.3배** |
| G 면 순회만 (`mesh()` 없음) | 0.001 | 49,388,323 | 1018.6배 |

### 7.2 읽는 법 — 예상이 빗나갔습니다

**설계 초안에서 세운 가설은 "정점마다 Ruby 호출을 3번 하는 루프 구조가 병목"이었고,
그에 따라 B·C·D 세 가지 최적화를 제안했습니다. 셋 다 아무 효과가 없었습니다(1.0~1.1배).**

실제 분포는 이렇습니다.

- **면 순회는 공짜입니다** (G: 0.001초). 씬 그래프 탐색은 비용이 아닙니다
- **삼각분할은 9%입니다** (F: 0.094초 / A: 1.061초)
- **나머지 91%가 PolygonMesh에서 데이터를 꺼내는 비용입니다.** 그리고 그 비용은
  Ruby 루프 구조가 아니라 **`normal_at`·`uv_at` 호출 자체**에 있습니다 — 루프를
  아무리 다듬어도(B·C·D) 줄지 않고, 호출을 아예 없애야만(E) 2.5배가 나옵니다

### 7.3 목표 수정

초안의 **1M tri/s 목표는 근거가 없었습니다.** F(추출이 공짜일 때)가 547,004 tri/s이고
이것이 SketchUp 삼각분할기를 쓰는 한 사실상의 상한입니다.

| 단계 | 현재 | 수정된 목표 | 근거 |
|---|---|---|---|
| 지오메트리 추출 | 48,487 tri/s (표본) / 29,363 tri/s (전체 모델) | **300,000 tri/s** | F 상한 547k의 55%. C API가 추출 비용을 크게 줄이되 삼각분할은 여전히 낸다 |
| 직렬화 | JSON 7.6초 / 140.6 MB | 0.5초 이내 / 33.8 MB | 바이너리, 복사 최소화 |
| 델타 왕복 | — | 50 ms 이내 | 편집 후 반영이 "즉시"로 느껴지는 한계 |

### 7.4 더 중요한 결론 — 빠르게가 아니라 적게

300,000 tri/s여도 1,000만 삼각형 모델은 **33초**입니다. 추출을 빠르게 하는 것만으로는
부족합니다. **추출량을 줄여야 합니다.**

| 전략 | 근거 |
|---|---|
| **정의 단위 캐싱** | 정의별로 변경 스탬프를 두고, 안 바뀐 정의는 다시 추출하지 않는다. 실측 재사용률 4.00(세종)/1.64(골프존)이고, 일반적인 편집은 정의 몇 개만 건드린다 |
| **최초 1회만 전량** | 이후는 델타. 6절의 트랜잭션 경계가 그 단위다 |
| **워커 스레드 추출** | Ruby는 메인 스레드에 묶이지만 C 확장은 그렇지 않다. UI 정지를 없앨 수 있다 |
| **법선 재계산 이관** | E가 2.5배인 것은 법선·UV를 안 꺼냈기 때문이다. 평면 면의 법선은 렌더러가 정점에서 계산할 수 있다. UV는 그럴 수 없다 |

**즉 C API 이관의 값어치는 "몇 배 빨라지나"보다 "무엇을 안 해도 되게 하나"에 있습니다.**

### 7.5 정의 단위 캐싱 구현 결과 (2026-09-07)

[`iris_probe.rb`](../tools/sketchup/iris_probe.rb)에 구현했습니다. 정의마다
`EntitiesObserver`를 붙여 변경을 감시하고, 안 바뀐 정의는 이전 추출 결과를 씁니다.
머티리얼 속성 변경은 `EntitiesObserver`로 잡히지 않으므로 `MaterialsObserver`를
별도로 답니다.

골프존 모델(삼각형 400,062 / 정의 706) 재동기화 실측:

| | 캐시 없음 | **캐시 적중 100%** | |
|---|---|---|---|
| 추출 시간 | 12,645.4 ms | **266.0 ms** | **47.5배** |
| 처리량 | 31,637 tri/s | **1,503,978 tri/s** | |
| 1000만 삼각형 환산 | 316.1초 | **6.6초** | |

**7.3절의 300,000 tri/s 목표를 5배 초과합니다.** 추출을 빠르게 한 것이 아니라
하지 않았기 때문입니다.

> ⚠ **이 표는 한 번 정정됐습니다.** 최초 기록은 6,915,283 tri/s / 1.4초 / 23배였는데,
> 캐시가 정의별 카운트를 자손까지 중복 계산하던 버그(삼각형이 400,062 대신 2,283,688로
> 집계) 때문에 부풀려진 값이었습니다. 버그를 고친 뒤 1차·2차 실행의 지오메트리 수치가
> 정확히 일치하는 것을 확인하고 위 값으로 갱신했습니다.

캐싱을 켜자 숨어 있던 버그 세 개가 연달아 드러났습니다 — 능력 플래그 미보존(판정문이
거짓을 말함), 텍스처 통계 혼동, 자손 카운트 중복. 셋 다 **2차 실행 리포트를 읽어야만
보이는** 것들이었습니다. 캐시는 "같은 입력에 같은 출력"을 요구하므로, 켜는 순간 숨어
있던 상태 의존성이 전부 드러납니다.

⚠ 이 수치는 **아무것도 바뀌지 않은 재동기화** 기준입니다. 실제 편집은 일부 정의를
무효화하므로 그만큼 다시 추출합니다. 다만 일반적인 편집이 정의 몇 개만 건드린다는 점,
그리고 최초 1회는 어차피 전량이라는 점에서 **구조는 검증되었습니다.**

### 7.6 이제 직렬화가 병목입니다

| 단계 | 캐시 전 | 캐시 후 |
|---|---|---|
| 추출 | 12,645.4 ms (62%) | 266.0 ms (**3.4%**) |
| JSON 기록 | 7,623.7 ms (38%) | 7,623.7 ms (**96.6%**) |

**병목이 추출에서 직렬화로 옮겨갔습니다.** 1절 4번(JSON 140.6 MB / 바이너리 33.8 MB)이
이제 가장 큰 항목이며, 바이너리 전환이 다음 우선순위입니다.

### 7.7 바이너리 직렬화 구현 결과 (2026-09-07)

`.irisb` 형식을 프로브와 변환기 양쪽에 구현했습니다(8절 참조).

| | JSON | **바이너리** | |
|---|---|---|---|
| 기록 시간 | 7,623.7 ms | **232.1 ms** | **32.8배** |
| 파일 크기 | 140.6 MB | **34.3 MB** | **4.1배** |
| — 매니페스트 | — | 0.55 MB | |
| — 지오메트리 | — | 33.78 MB | 1절 예측치 33.8 MB와 일치 |

**7.3절의 두 목표(0.5초 이내 / 33.8 MB)를 모두 달성했습니다.**

전체 동기화 시간:

| | 캐시·JSON | **캐시·바이너리** | |
|---|---|---|---|
| 추출 | 12,645.4 ms | 202.2 ms | |
| 기록 | 7,623.7 ms | 232.1 ms | |
| **합계** | **20,269 ms** | **434 ms** | **46.7배** |

#### 검증

같은 씬을 JSON 입력과 바이너리 입력으로 각각 변환해 결과 `.glb`를 비교했습니다.

- 구조(nodes / meshes / materials / bufferViews / images / textures / **accessors**) **전부 동일**
- 지오메트리 바이트는 **0.1347%**가 다르며, **전부 UV(VEC2)** 이고 최대 절대차가
  **1.192e-07 = f32의 1 ULP** 입니다

원인은 바이너리가 UV를 f32로 저장하므로 변환기의 V 뒤집기(`1.0 - v`)가 원본 double이
아니라 f32 값에서 계산되기 때문입니다. UV 좌표에서 1 ULP는 무시할 수 있는 크기이고,
f64로 저장하면 파일이 커지므로 **이 차이는 수용합니다.**

> 이 검증 과정에서 기존 코드의 버그를 하나 찾았습니다. POSITION 접근자의 min/max를
> double로 계산해 **실제 저장된 f32 데이터를 벗어나 있었습니다**(min이 데이터보다 큼).
> glTF 사양 위반입니다. f32로 내린 뒤 계산하도록 고쳤습니다.

## 8. `.irisb` 파일 형식 (구현됨)

```
오프셋  크기  내용
   0     8    magic "IRISSCN1"
   8     4    version (u32 LE) = 1
  12     4    reserved
  16     8    json_len (u64 LE)
  24     8    bin_len  (u64 LE)
  32     ?    JSON 매니페스트 (8바이트 정렬까지 공백 패딩)
   ?     ?    바이너리 블롭
```

매니페스트는 기존 `.iris.json` 과 같은 구조이되, 메시의 배열 필드가 값 대신
블롭 참조입니다.

```json
"meshes": [{
  "material":  "mat_239",
  "positions": {"off": 0,      "count": 72},
  "normals":   {"off": 288,    "count": 72},
  "uvs":       {"off": 576,    "count": 48},
  "indices":   {"off": 768,    "count": 36}
}]
```

- `positions`·`normals`·`uvs` 는 **f32 리틀엔디언**, `indices` 는 **u32 리틀엔디언**
- `count` 는 요소 수(바이트 수가 아니다)
- **인터리브하지 않습니다.** 프로브가 이미 분리된 배열을 갖고 있어 재배열 비용이
  0이고, glTF도 속성별 접근자를 씁니다

Ruby 쪽은 `Array#pack('e*')` / `pack('V*')` 로 씁니다 — C 구현이라 요소당 Ruby
호출이 없고, 이것이 JSON 대비 32.8배의 실체입니다.
