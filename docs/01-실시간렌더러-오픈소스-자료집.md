# Enscape형 실시간 렌더링 프로그램 구축 — 오픈소스 & 기술 자료집

> 작성일: 2026-09-07
> 목표: Enscape / Twinmotion / D5 Render 계열의 **AEC용 실시간 렌더러**를 자체 구축하기 위한 기술 지도

---

## 0. 먼저 — Enscape의 진짜 해자(垓子)는 렌더러가 아니다

Enscape을 만든다고 하면 대부분 "렌더링 엔진"을 떠올리지만, 제품을 분해하면 렌더러는 4개 축 중 하나에 불과합니다. 오픈소스 자료의 밀도도 축마다 극단적으로 다릅니다.

| 축 | 내용 | 오픈소스 가용성 | 실제 난이도 |
|---|---|---|---|
| **① 렌더링 코어** | 하이브리드 RT, GI, 디노이징, 업스케일링 | ★★★★★ 매우 풍부 (NVIDIA/AMD가 SDK를 다 공개) | 중 |
| **② CAD/BIM 라이브 링크** | Revit·SketchUp·Rhino·ArchiCAD 플러그인 + 증분 동기화 | ★☆☆☆☆ 거의 없음 (각 사 폐쇄 SDK) | **최상** |
| **③ 대규모 씬 처리** | BIM 모델 = 수천만 폴리곤 / 수만 오브젝트 / 수만 머티리얼 | ★★★☆☆ (Nanite류 라이브러리 공개됨) | 상 |
| **④ 에셋·머티리얼 라이브러리** | 가구·식생·사람·재질 수천 종, 큐레이션 | ★★★☆☆ (CC0 소스 있으나 양·품질 확보가 일) | 중(그러나 방대) |

**결론:** ①은 NVIDIA/AMD SDK를 조립하면 6~12개월 내 데모 수준 도달이 현실적입니다. 제품의 성패는 **②(라이브 링크)와 ③(대규모 씬)**에서 갈립니다. 아래 자료집도 이 우선순위로 읽으시길 권합니다.

## 1. 구축 경로 3가지 — 어디서 출발할 것인가

### 경로 A. 상용 게임엔진 위에 (Twinmotion 방식)
- **Unreal Engine 5** — Lumen(동적 GI) + Nanite(가상 지오메트리)가 이미 완성형. Twinmotion이 정확히 이 방식.
- 장점: 렌더링 품질 즉시 확보, VR/애니메이션/포스트프로세스 전부 무료 제공
- 단점: **매출 100만 USD 초과분에 5% 로열티**, 엔진 내부 개조 비용 큼, 실행파일 비대(수 GB)
- 대안 오픈소스: **[Godot 4](https://github.com/godotengine/godot)** (MIT, 로열티 0, Vulkan 렌더러 — 다만 AAA급 GI는 직접 구현 필요), **[O3DE](https://github.com/o3de/o3de)** (Apache 2.0, Linux Foundation, Atom 렌더러, ECS 구조로 대규모 씬에 유리)

### 경로 B. 오픈소스 렌더 프레임워크 위에 (★ 권장)
게임엔진의 군더더기 없이 렌더링에만 집중. **AEC 실시간 렌더러에 가장 적합.**
- **NVIDIA Donut + RTXDI/RTXPT + NRD + Streamline** 조합 → 사실상 "Enscape 렌더링 코어 키트"
- **Autodesk Aurora** → 이미 "실시간 GPU 패스트레이싱 + OpenUSD Hydra 델리게이트"라 AEC 워크플로에 정조준되어 있음

### 경로 C. 밑바닥부터 (Vulkan/DX12 직접)
- 학습·완전한 통제력 목적이면 유효하지만 제품화까지 3~5년. 팀 규모가 작다면 비권장.
- 시작점: `nvpro-samples/vk_raytracing_tutorial_KHR`

> **추천:** 경로 B로 코어를 만들되, ②라이브 링크는 처음부터 별도 팀/트랙으로 병행. 렌더러가 아무리 좋아도 Revit에서 원클릭으로 안 열리면 제품이 아닙니다.

## 3. 셰이더 언어 / 툴체인

- **Slang** — [shader-slang.org](https://shader-slang.org/) · Khronos가 2024년 말부터 관리. **HLSL 상위호환**이며 SPIR-V / HLSL / GLSL / WGSL / Metal 로 전부 크로스 컴파일. 모듈·인터페이스·제네릭 지원으로 대형 셰이더 코드베이스 유지보수가 크게 쉬워짐. Vulkan SDK에 동봉.
  - [Vulkan 공식 Slang 가이드](https://docs.vulkan.org/guide/latest/slang.html)
  - [Vulkan 셰이더 언어 비교 문서](https://docs.vulkan.org/guide/latest/high_level_shader_language_comparison.html)
- **DXC / SPIRV-Cross / glslang** — 전통적 조합 (Slang 미채택 시)
- **MaterialX** — [github.com/AcademySoftwareFoundation/MaterialX](https://github.com/AcademySoftwareFoundation/MaterialX) · 머티리얼 그래프 교환 표준. Revit/3ds Max/USD와의 재질 상호운용에 사실상 필수
- **OpenPBR** — MaterialX 기반 표준 서피스 모델. V-Ray/Arnold 등과 재질 룩을 맞출 때의 공통 기준

## 5. 전역 조명(GI) 기법 — 선택지 정리

건축 실내는 **간접광이 전부**입니다. GI 방식 선택이 제품 성격을 결정합니다.

| 기법 | 대표 구현 | 특징 | AEC 적합성 |
|---|---|---|---|
| **ReSTIR DI/GI/PT** | RTXDI | 다광원 + 다바운스 실시간. 현재 최고 품질 | ★★★★★ (RT GPU 필요) |
| **NRC (뉴럴 캐시)** | NVIDIA NRC | 무한 바운스 근사, 매우 밝은 실내에 유리 | ★★★★☆ (NVIDIA 전용) |
| **SHaRC (해시 캐시)** | NVIDIA SHARC | 벤더 무관, 구현 부담 낮음 | ★★★★★ |
| **DDGI (조사장 프로브)** | [RTXGI-DDGI](https://github.com/NVIDIAGameWorks/RTXGI-DDGI) · [알고리즘 문서](https://github.com/NVIDIAGameWorks/RTXGI-DDGI/blob/main/docs/Algorithms.md) | 안정적·저렴, 디테일은 약함. 대형 씬에 검증됨 | ★★★★☆ |
| **SDF/Voxel GI** | AMD Brixelizer GI, NVIDIA VXGI | RT 하드웨어 불필요 | ★★★☆☆ (구형 GPU 지원용) |
| **SSGI (스크린스페이스)** | Blender EEVEE Next, [SSGI 해설글](https://gamehacker1999.github.io/posts/SSGI/) | 가장 저렴, 화면 밖 정보 없음 | ★★☆☆☆ (폴백용) |
| **Lumen (UE5)** | Unreal Engine 5 | 완성형이나 고사양 요구 | 경로 A 선택 시 |

**실무 권장 조합:** `ReSTIR DI(직접광) + SHaRC 또는 NRC(간접광) + NRD(디노이즈) + DLSS/FSR(업스케일)`
→ 이것이 현재 실시간 패스트레이싱 제품의 표준 파이프라인입니다.

**참고 학습 구현:** [DDGI Minecraft (Vulkan)](https://github.com/helenl9098/Dynamic-Diffuse-Global-Illumination-Minecraft) — 2019 SIGGRAPH DDGI 논문의 읽기 좋은 실습 구현

## 7. 업스케일링 / 프레임 생성

실시간 패스트레이싱은 **내부 해상도를 낮추고 업스케일하는 것이 전제**입니다. 선택이 아니라 필수 구성요소입니다.

- **NVIDIA Streamline** — [github.com/NVIDIAGameWorks/Streamline](https://github.com/NVIDIAGameWorks/Streamline) · **오픈소스 크로스-IHV 플러그인 레이어**. DLSS/FSR/XeSS를 하나의 인터페이스로 통합. **여기서 시작하는 것이 정답**
- **NVIDIA DLSS SDK** — [github.com/NVIDIA/DLSS](https://github.com/NVIDIA/DLSS) (Super Resolution / Ray Reconstruction / Frame Generation)
- **AMD FidelityFX FSR 3.1+** — FidelityFX SDK 내. 3.1부터 **프레임 생성이 업스케일러와 분리**되어 DLSS·XeSS·자체 TAAU와 조합 가능
- **Intel XeSS SDK** — [github.com/intel/xess](https://github.com/intel/xess)
- 참고: [DLSS vs FSR vs XeSS 종합 해설](https://wccftech.com/roundup/nvidia-dlss-vs-amd-fsr-vs-intel-xess-everything-you-need-to-know/) · [업스케일링 동작 원리 (2026)](https://eatcreatesleep.net/how-upscaling-dlss-xess-fsr-actually-works/)

> **필수 요구사항:** 모든 업스케일러는 **모션 벡터 + 깊이 버퍼 + 지터링된 카메라**를 요구합니다. 렌더러 설계 초기부터 이 3가지를 파이프라인에 넣어두지 않으면 나중에 갈아엎게 됩니다.

## 8. 대규모 지오메트리 (Nanite류)

BIM 모델은 수천만 폴리곤 + 수만 개 개별 오브젝트입니다. **드로우콜과 LOD가 병목이 됩니다.**

| 자료 | 링크 | 내용 |

## 10. BIM / CAD 임포트 — ②번 축의 핵심

### 10.2 네이티브 호스트 앱 라이브 링크 (제품화의 결정적 관문)

여기가 오픈소스가 사실상 없는 구간입니다. **각 사 SDK를 직접 다뤄야 합니다.**

| 호스트 | API | 라이브 동기화 접근법 |
|---|---|---|
| **Revit** | Revit API (.NET) | `IExternalApplication` + `IUpdater`로 문서 변경 이벤트 수신 → 변경된 Element만 증분 전송. `DirectContext3D`로 역방향 뷰포트 오버레이도 가능 |
| **SketchUp** | C API (SDK) + Ruby API | Ruby `Sketchup::EntityObserver`/`ModelObserver`로 변경 감지, C API로 지오메트리 추출 |
| **Rhino / Grasshopper** | RhinoCommon (.NET) | `RhinoDoc` 이벤트 구독. Grasshopper 컴포넌트로 파라메트릭 연동까지 확장 가능 |
| **ArchiCAD** | ArchiCAD API (C++) | Add-On 형태 |
| **Vectorworks** | Vectorworks SDK | Plug-in |
| **Blender** | Python API (`bpy`) | `depsgraph_update_post` 핸들러 |
| **3ds Max** | 3ds Max SDK | 참고: IfcOpenShell이 임포터 제공 |

**참고 제품 동작 조사:**
- [Lumion LiveSync for Revit](https://apps.autodesk.com/RVT/en/Detail/Index?id=1257010617153832891&appLang=en&os=Win64) — Autodesk App Store에서 실제 배포 형태·권한 요구 확인 가능
- [D5 Sync for Revit](https://www.d5render.com/workflow/revit) — 지오메트리·머티리얼·카메라 실시간 동기화 사양
- [SketchUp ↔ Revit 상호운용 공식 문서](https://help.sketchup.com/en/extending-sketchup/revit-interoperability) — BIM 데이터(레벨/태그) 매핑 방식 참고

**폐쇄 포맷 직접 읽기(RVT/DWG):** 오픈소스로는 불가능에 가깝습니다. 상용 **Open Design Alliance(ODA)** 라이브러리 또는 **CAD Exchanger** 라이선스가 현실적 선택지입니다. 다만 초기에는 IFC + 호스트 플러그인 익스포트 방식으로 충분합니다.

**증분 동기화 설계 핵심:** 전체 재변환은 대형 모델에서 수 분이 걸립니다. Element GUID 기반 델타 추적(추가/수정/삭제) + 인스턴싱(같은 패밀리 타입은 지오메트리 공유) + 백그라운드 스레드 테셀레이션이 필수입니다. 이 부분이 Enscape 체감 성능의 8할입니다.

## 15. 단계별 로드맵 (제안)

### Phase 0 — 기술 검증 (1~2개월)
1. `nvpro-samples/vk_raytracing_tutorial_KHR` 완주 → RT 파이프라인 체득
2. **RTXPT 샘플을 그대로 빌드해서 자체 IFC 모델 하나를 띄워보기** ← 가장 빠른 현실성 판단
3. `NRD-Sample` 실행 → 디노이징 품질/비용 감각 확보
4. Revit 플러그인 "Hello World" + Element 순회 → 지오메트리 덤프

> Phase 0의 목적은 코드가 아니라 **의사결정**입니다. 이 4개를 마치면 경로 A/B/C 중 무엇을 갈지 확신이 생깁니다.

### Phase 1 — 렌더링 코어 (3~6개월)
- Donut 또는 Falcor 기반 프레임 골격
- glTF/USD 로딩 → BVH 구축 → ReSTIR DI + SHaRC GI + NRD + Streamline(DLSS/FSR)
- 카메라 지터 + 모션벡터 파이프라인 **초기부터** 확보
- 톤매핑(ACES/AgX), 노출, 화이트밸런스, DOF, 블룸
- 태양 위치(위도/경도/일시) + 물리 기반 하늘(Hosek-Wilkie 또는 Bruneton) + HDRI 환경광

### Phase 2 — BIM 파이프라인 (3~6개월, Phase 1과 병행)
- IfcOpenShell 또는 web-ifc 코어로 IFC 임포트
- Revit 라이브 링크 (증분 동기화 · GUID 델타 추적 · 인스턴싱)
- 재질 매핑 계층 (Revit Material → MaterialX/OpenPBR → 자체 셰이더)
- nv_cluster_lod_builder로 대형 모델 LOD 자동 생성

### Phase 3 — 제품화 (6~12개월)
- 에셋 라이브러리 + 배치 도구 (식생/가구/인물)
- 출력: 스틸 / 360 파노라마 / 동영상 / 독립 실행형 뷰어
- OpenXR VR 모드
- SketchUp·Rhino·ArchiCAD로 호스트 확장
- 라이선싱·업데이트·크래시 리포팅 인프라

## 20. 남은 결정 사항

이 자료집으로 다음 단계를 진행하기 전에 확정이 필요한 항목입니다.

1. **타깃 GPU 범위** — RTX 하드웨어 필수인가, 구형 GPU 폴백(Brixelizer GI)도 지원할 것인가? → GI 아키텍처 전체가 여기서 갈립니다
2. **1순위 호스트 앱** — Revit / SketchUp / Rhino 중 어디부터? → 국내 시장이면 Revit·SketchUp, 설계사무소 규모에 따라 다름
3. **경로 A/B/C 선택** — 팀 규모와 목표 시점에 직결
4. **라이선스 정책** — 클로즈드 상용 제품인가, 오픈소스인가? → GPL/LGPL 코드 사용 가능 여부가 결정됨
5. **플랫폼** — Windows 전용(경쟁사 대부분) vs 크로스플랫폼
