# 10. 배선 검사표

호스트(SketchUp)에서 화면까지, 값이 건너가는 선을 하나씩 세고 **반대편에
제대로 도착한다는 근거가 무엇인지**를 적습니다.

## 왜 이 문서가 있는가

2026-09-11 하루에 조용히 틀린 배선이 넷 나왔습니다. 넷 다 **오류를 내지
않았습니다**:

| | 무엇이 틀렸나 | 어떻게 알았나 |
|---|---|---|
| 하늘 | 설정을 하늘 객체가 **생기기 전에** 밀어 넣어 무시됨 | 실내라 화면으로는 못 봄. 엔진의 자체 수치가 기본값 그대로인 것을 읽고 |
| 모델 전환 | 전체 전송으로 올려 놓고도 재사용 경로가 **이전 모델의 씬**을 다시 보냄 | 렌더러 화면이 비어서 |
| IES 방위 | 0도 기준을 로컬 +X 로 봤는데 **+Y** 였음 — 90도 회전 | 통제 시험(광원 하나 + 흰 바닥)에서 웅덩이 방향이 Enscape 와 직각 |
| 설정 저장 | 저장이 **오지 않을 수도 있는 다음 프레임**에 걸려 있었음 | 이 검사에서 |

공통점이 있습니다. **한쪽에서 값을 잘 만들었고, 반대편에 도착하는지는 아무도
안 봤습니다.** 그래서 "참조는 되는가"가 아니라 **"도착한다는 근거가
무엇인가"**로 묻습니다.

## 증거 등급

| 등급 | 뜻 |
|---|---|
| **측정** | 이 프로젝트에서 관측으로 확인했습니다. 재현 방법이 있습니다. |
| **추론** | 양쪽 코드를 읽어 맞다고 판단했습니다. 관측은 없습니다. |
| **가정** | 근거 없이 그렇게 두었습니다. **여기가 위험한 자리입니다.** |

오늘 틀린 넷은 전부 `가정` 이었거나, `추론` 인데 추론이 빗나간 것이었습니다.

## 10.1 규약 — 단위·좌표계·부호

| 배선 | 규약 | 등급 | 근거 |
|---|---|---|---|
| 길이 단위 | 인치 -> 미터 (`INCH_TO_M = 0.0254`), 호스트에서 변환 | 측정 | 실물 치수와 화면 크기가 맞음 |
| 상방 축 | 호스트 Z-up -> 엔진 Y-up, `(x,y,z) -> (x,z,-y)` | 측정 | 구도 맞춤(사용자 확인). 씬 루트와 카메라 메시지 **두 곳**이 같은 식 |
| 태양 방향 | `toward` 는 **모델에서 태양을 향하는** 방향. 빛은 그 반대 | 측정 | 그림자가 화면 어느 쪽으로 뻗어야 하는지 계산해 견줌 (커밋 `057e2c7`) |
| 광원 프록시 정면 | 로컬 **+Z** (Donut 은 -Z 규약이라 X축 180도 자식 노드로 뒤집음) | 측정 | `iris_lights_axis.rb` — 43개 인스턴스 전부 |
| **IES 가로각 0도** | 프록시의 로컬 **+Y** | 측정 | 통제 시험 (09번 8-g). **원래 +X 로 보고 90도 틀려 있었습니다** |
| IES 격자 축 | 폭 = 세로각(0~180), 높이 = 가로각(-180~180) | 측정 | 같은 통제 시험에서 웅덩이 비율 1.64:1 이 배광의 29.8도:18.0도 와 일치 |
| 카메라 화각 | `fovIsHeight` 로 수직/수평 구분, 종횡비로 환산 | 측정 | 6.5% 어긋남을 잡아 고친 뒤 구도 일치 |
| 사각 광원 세기 | Enscape `Luminosity` 는 **lm 1:1** | 측정 | 슬라이더 값과 XML 값 대조 (09번 8-c) |
| 측광 배율 | 1.0 렌더러 단위 = 5000 cd/m² | 추론 | 화면이 타지 않는다는 것 말고 독립된 확인이 없습니다 |
| 발광 재질 단위 | `emissiveCd` 를 cd/m² 로 해석 | 추론 | 3000~7000 이 실제 LED 패널 휘도와 맞는다는 것이 근거 |
| 텍스처 색공간 | 색상 텍스처는 sRGB | 추론 | 코드에 명시. 눈으로만 확인 |
| UV | 호스트가 `1 - v` 로 뒤집어 보냄 | 측정 | 텍스처가 뒤집혀 보이지 않음 |

## 10.2 선은 있는데 **쓰이지 않는** 것

프로토콜에는 있고 렌더러가 안 쓰는 필드입니다. 전부 확인했고, 버려도 되는
이유가 있습니다.

| 필드 | 왜 안 쓰나 |
|---|---|
| `pbr.ior` | **엔진 재질에 일반 IOR 필드가 없습니다** (`SceneTypes.h` 의 `ior` 는 hair 전용). 버릴 수밖에 없습니다 |
| ~~`pbr.opacity`~~ | **2026-09-11 연결했습니다** (09번 8-i). 미지정 센티널이 필요했습니다 — 기본값 1 로 두면 Opacity 항목이 없는 Enscape 재질이 전부 불투명으로 뒤집힙니다 |
| `pbr.bump` · `normalIntensity` · `bumpType` | 노멀맵을 내보내지 않습니다. 넣으려면 호스트부터 |
| ~~`pbr.solidGlass`~~ · `etype` | `solidGlass` 는 **연결했습니다** (09번 8-i). `etype` 은 이 모델들이 전부 `GENERIC` 이라 쓸 데가 없습니다 |
| `texture.widthM` · `heightM` | **UV 에 이미 배율이 들어 있습니다** (`uv_at` 가 정규화된 값을 줌). 진단용 |
| `view.hasHeight` | 평행 투영 전용. 호스트가 항상 원근입니다 |
| `sun.dark` | SketchUp 의 '어두움' 슬라이더. 엔진에 대응이 없습니다 |
| `node.layer` · `entityId` · `persistentId` | 델타 추적은 호스트가 합니다. 렌더러는 안 봅니다 |
| `isGroup` · `instanceCount` · `iesAsym` | 진단·통계용 |

`solidGlass` 와 `pbr.opacity` 둘은 **2026-09-11 에 연결했습니다** — 세종
모델에서 "중앙부가 왜 희미한가"를 따라가다 나왔습니다(09번 8-i). 다만 그
모델은 반투명 재질 12개 중 0개에만 Enscape 값이 있어서, **연결해도 그
모델은 달라지지 않습니다.** 포르쉐처럼 Enscape 로 정성껏 만든 모델에서
효과가 납니다.

## 10.3 캐시 — 낡은 것을 내줄 수 있는 자리

오늘 넷 중 둘이 캐시에서 나왔습니다. 전수로 셉니다.

| 캐시 | 키 | 수명 | 자물쇠 |
|---|---|---|---|
| `Probe.@scene` | — | 프로세스 | `scene_model_ok?` (모델 키) ✓ |
| `DefCache.@entries` | entityID | 프로세스 | `check_model` ✓ |
| `Probe.@mat_records` | 재질 id | 프로세스 | `forget_materials` (모델 전환 시) ✓ |
| `Link.@sent_gen` | 정의 id | 프로세스 | 모델 전환 · 세션 변경 · `need_full` ✓ |
| `Link.@last_sig` | — | 프로세스 | 모델 전환 시 nil ✓ |
| 텍스처 내보내기 | `mat_<id>.png` | **디스크** | 폴더가 모델 제목별 ✓ |
| `s_meshCache` (렌더러) | 정의 id | 프로세스 | **모델 키** (2026-09-11 추가) |
| `s_iesProfiles` (렌더러) | `파일@폭x높이` | 프로세스 | 크기를 키에 넣음 ✓ |

### 왜 `s_meshCache` 에 자물쇠를 더 달았나

키가 `def_<entityID>` 인데 **entityID 는 모델마다 다시 매겨집니다.** 다른
파일을 열면 같은 번호가 전혀 다른 정의를 가리킵니다.

실제로는 링크가 모델 전환을 감지해 전체를 다시 보내므로 일어나지 않습니다.
그런데 **그 불변식이 반대편에만 있습니다.** 링크가 나중에 똑똑해지면
("이 모델은 전에 봤으니 재사용") 여기가 조용히 뚫립니다. 같은 날 호스트
쪽에서 정확히 그 사고가 났으므로, 문을 두 군데 답니다.

⚠ 한계: 저장 안 한 모델은 경로가 비어 **제목으로만** 갈립니다. 제목까지
같은 빈 모델 둘은 구별 못 하고, 그때는 링크 쪽 판정에 기댑니다.

### 텍스처 폴더의 한계

`textures/<모델 제목>/` 이라 **제목이 같으면** 다른 파일이라도 섞입니다.
`model.title` 은 확장자 뺀 파일 이름이므로, 다른 폴더의 동명 파일이 그
경우입니다. 경로로 바꾸면 없어지지만 폴더 이름이 길어집니다 — 지금은
한계를 적어 두는 것으로 둡니다.

## 10.4 설정 — 파일 · UI · 엔진

2026-09-11 에 새로 생긴 선입니다(09번 8-h). 셋이 한 값을 두고 만납니다.

```
%LOCALAPPDATA%\IRIS\settings.json   <->   iris::Settings::Get()   ->   엔진
                                            (IRIS 패널이 편집)
```

| 배선 | 등급 | 근거 |
|---|---|---|
| 흐림 -> 절차적 하늘 | 측정 | 흐림 0 -> offset 1.000, 흐림 1 -> offset 0.000 (엔진 자체 컨트롤로 읽음) |
| 흐림 -> 화면 | 측정 | 실외 모델, 노출 고정, 같은 구도. 맑음이 밝고 대비가 섬 |
| 노출 -> 톤매퍼 | 측정 | 껐다 켜며 화면이 바뀌는 것 확인 |
| 면광원 토글 -> 씬 그래프 | 측정 | 트레이스에 `면광원 — 발광 지오메트리` / `구면 근사` |
| IES 토글 -> 배광 | 측정 | 트레이스에 `IES 배광 — 1종을 광원 43개가 씁니다` |
| **UI -> 파일** | 측정 | 아래 참고 — 이 검사에서 고쳤습니다 |

### 저장이 "오지 않을 수도 있는 프레임"에 걸려 있었습니다

처음 구현은 이랬습니다:

```cpp
// 바뀜을 표시해 두고
m_irisSettingsDirty = true;
// 활성 위젯이 없는 프레임에 쓴다
if (m_irisSettingsDirty && !ImGui::IsAnyItemActive()) { s.Save(); ... }
```

슬라이더가 끄는 내내 바뀜을 돌려주니 매 프레임 디스크에 쓰는 것을 막으려던
것입니다. 그런데 **그 '다음 프레임'이 안 올 수 있습니다**:

- 렌더러는 포커스를 잃으면 렌더 루프를 멈춥니다 (`Render when out of focus`
  가 기본 꺼짐)

  > 이 사실을 여기 적어 두고도 **라이브 링크에 대한 결론을 안 냈습니다.**
  > 사용자는 SketchUp 에서 작업하므로 렌더러는 거의 항상 배경이고, 그러면
  > 보낸 씬도 반영되지 않습니다. 하루 뒤 6번 A/B 에서 그것에 걸렸습니다
  > (10.4-b). 같은 문장을 두 번 읽고서야 알았습니다.
- `IRIS` 항목을 접으면 본문이 아예 안 돕니다

둘 중 하나면 변경이 조용히 사라집니다. 실제로 파일과 화면이 어긋난 것을
보고도 그때는 넘어갔고, 이 검사에서 원인을 찾았습니다.

고침은 **확정된 사건**에 거는 것입니다:

```cpp
// 체크박스 — 클릭 한 번이 곧 사건
if (ImGui::Checkbox("Auto exposure", &s.autoExposure)) apply = save = true;
// 슬라이더 — 손을 뗄 때 정확히 한 번
if (ImGui::SliderFloat("Cloudiness", &s.cloudiness, 0, 1, "%.2f")) apply = true;
save |= ImGui::IsItemDeactivatedAfterEdit();
```

미래의 프레임에 기대지 않습니다.

## 10.4-b 재질 품질 배선 (2026-09-12 추가분)

11번의 1~3번과 글꼴 작업으로 놓은 선입니다. **각 줄에 "무엇을 보면 살아
있는 줄 아는가"(증인)를 함께 적습니다** — 증인 없는 줄이 조용히 죽는
줄입니다.

| 값 | 경로 | 증인 | 등급 |
|---|---|---|---|
| 텍스처 알파(채널·최솟값·구멍비율) | 프로브 `texture_alpha_stats` → `texture.alpha` → `Texture::NeedsAlphaTest` → `AlphaTested` | 로그 `텍스처 N개 · 그중 알파 컷아웃 M개`, 화면(타공판 구멍) | 측정 |
| 알파 컷아웃 켬/끔 | 설정 `alpha_cutout` → `SetAlphaCutout` | 위 로그의 M 이 0/1 로 바뀜 | 측정 |
| OMM 섞인 메시 회피 | `OmmBaker::CreateOpacityMicromaps` | 로그 `섞인 메시 N개를 건너뛰었습니다` | 측정 |
| 단면/덩어리 | `IsSolidGlass` → `MaterialHints.thinSurface` → `MaterialEx` → `PTMaterial::ThinSurface` | 로그 `유리 — 단면 N · 덩어리 M`, 화면(커튼월 투과) | 측정 |
| 굴절률 | `IndexOfRefraction` → `MaterialHints.ior` → `PTMaterial::IoR` | 로그 `저작자 굴절률 K개` | 측정(합성 씬) |
| 모델별 재질 이름 | `src.sourceFile/Title` → `Material::modelFileName` | 로그의 `<모델>.<재질>.material.json` | 측정 |
| 덮어쓰기 경고 | `MaterialsBaker` 로드 분기 | 로그 `저장된 재질 파일 N개가 호스트 값을 덮었습니다` | 측정 |
| 덮어쓰기 삭제 | `IrisOverrideFiles`/`IrisDeleteOverrides` + `ForgetLastScene` | UI 개수 0 으로, 로그 `씬 수신`(같은 씬 수용) | 측정 |
| 한글 UI | `m_koreanFont`(글리프 범위) | 삭제 대화상자의 파일명이 한글로 | 측정 |
| 범프 → 노멀맵 | `BumpAmount` → `HeightToNormal` → `normalTextureScale` + 정점 탄젠트 | 로그 `범프 — 노멀맵 N개`, 화면(잔디 결) | 측정·A/B |
| 거칠기 기본값 | 설정 `roughness_default` → `SetRoughnessDefault` → `GuessSurface` | 로그 `거칠기 추측 — 기본값 X 로 간 재질 N개` (추적 파일에도) | 측정·A/B |
| 이름 규칙 | 설정 `surface_name_rules` → `SurfaceGuess.cpp` 표 | 같은 로그 줄의 `이름 규칙: 가죽 1개 · 목재 2개 …` | 측정·시험 81개 |
| 배경에서도 그리기 | 설정 `render_unfocused` → `ApplyIrisSettings` → `m_ui.RenderWhenOutOfFocus` | 렌더러를 배경에 두고 동기화 → 화면이 바뀜 | 측정 |
| 대기 작업이 루프를 깨움 | `Sample::ShouldRenderUnfocused` → `HasPendingScene/Camera` | 추적의 `Animate: 대기 씬을 발견` (창을 안 건드리고) | 측정 3/3 |
| 진단 추적 | `IRIS_TRACE_LOG` → `iris::InstallTraceHooks()` (프로세스 시작) | 파일 첫 줄 `=== IRIS 추적 시작 ===` | 측정 |
| 반영 상태 보고 | `IrisBridge::BuildHelloAck` → `applied`/`pending`/`dropped` → 호스트 `check_applied` | 최소화한 채 두 번 보내면 `⚠ 지난번에 보낸 씬이 아직 화면에 올라가지 않았습니다` | 측정·시험 13개 |
| 최소화 알림 | `Sample::IrisBeforeFrame` → `glfwRequestWindowAttention` | 로그 `새 씬이 왔는데 창이 최소화되어 있습니다` · 작업 표시줄 깜빡임 | 측정 |

### 합성 씬이 굴절률을 증명했습니다

실제 두 모델에는 **Enscape 굴절률이 하나도 없습니다**(`저작자 굴절률 0개`).
그래서 이 경로는 화면까지 한 번도 안 탔습니다 — 조용히 죽어 있어도 몰랐을
자리입니다.

`out/test/wiring.irisb` 에 유리 셋(미지정 · 1.52 · 1.33)을 심어 두고
`iris_send.py` 로 쐈습니다:

```
IRIS: 유리로 해석한 머티리얼 3개 (그중 저작자 지정 2)
IRIS: 유리 — 단면 1개 · 덩어리 2개 · 저작자 굴절률 2개
IRIS: 텍스처 0개 · 그중 알파 컷아웃 2개 (프로브가 못 잰 것 1)
IRIS: 조명 — 점 2 · 스포트 3 · 총 광속 45500 lm · 발광 재질 1
```

세 줄 모두 심어 둔 값과 맞습니다. **SketchUp 을 열지 않고** 이 경로를
언제든 다시 확인할 수 있습니다.

### 어긋난 것 하나 — 배선이 아니라 **기대값이 낡았습니다**

`스포트 3` 이 나왔는데 생성기의 기대값은 4 였습니다. 배선이 끊긴 줄 알고
들여다봤더니, **"Area lights as emissive geometry" 기본값이 켬으로 바뀐 뒤**
사각 광원이 발광 지오메트리로 가면서 스포트에서 빠진 것이었습니다.
기대값에 그 조건을 적어 뒀습니다.

> 기대값도 **낡습니다.** 설정이 기대값을 바꾸면 그 설정을 기대값 옆에
> 적어야 합니다.

### 고친 것 — **배경에 있으면 씬이 반영되지 않았습니다** (2026-09-12)

6번 A/B 를 하다 두 번 걸렸습니다. 렌더러를 새로 띄우고 보낸 전체 동기화가
적용되지 않는데, 호스트 쪽은 성공으로 보입니다:

```
[IRIS 링크] 전송 35.9 ms  962 MB/s
[IRIS 링크]   └ 열기 0.1 · Hello 0.2 · 쓰기 24.4 · Ack 대기 5.9 · Bye 0.0 ms
[IRIS 링크] 렌더러 화면이 바뀌어야 합니다.     ← 안 바뀝니다
```

#### 첫 진단은 틀렸습니다

처음에는 "시작 씬(bistro)을 읽는 동안 도착한 씬이 대기열에서 버려진다"고
적었습니다. **틀렸습니다.** 버려지는 것이 아니라 **아무도 집어 가지
않습니다.**

틀린 채로 넘어갈 뻔한 이유가 있습니다. 그때 진단이 **첫 `LoadIrisb` 에서야**
파일 갈고리를 걸었습니다. 그래서 씬을 한 번도 못 읽으면 추적 파일 자체가
안 생기고, "씬이 안 왔다" 와 "갈고리가 아직 안 걸렸다" 를 가릴 수 없었습니다.
`IrisTrace.h` 로 빼서 **프로세스 시작에서** 걸도록 바꾸니 한 번에 보였습니다.

#### 진짜 원인 — Donut 의 프레임 루프가 포커스로 잠깁니다

```cpp
// External/Donut/src/app/DeviceManager.cpp — AnimateRenderPresent
if (m_windowVisible && (m_windowIsInFocus || ShouldRenderUnfocused() || ...))
{
    Animate(elapsedTime, true);   // ← 여기서 Sample::Animate 가 대기 씬을 봅니다
    ... Render(); Present();
}
else if (m_windowVisible)
{
    Animate(elapsedTime, false);  // ← 이때는 ShouldAnimateUnfocused() 인 패스만
}
```

훅이 **둘**이고 둘 다 기본값이 거짓입니다.

| 훅 | 무엇을 여는가 |
|---|---|
| `IRenderPass::ShouldAnimateUnfocused()` | 포커스가 없을 때 `Animate()` 만 |
| `IRenderPass::ShouldRenderUnfocused()` | 프레임 전체(Animate + Render + Present) |

대기 씬을 집어 가는 코드는 `Sample::Animate` 안에 있습니다. **사용자는
SketchUp 에서 작업하므로 렌더러 창은 거의 항상 배경입니다.** 그러면
`Sample::Animate` 가 돌지 않고, 씬은 `IrisBridge::m_pending` 에 그대로
앉아 있습니다. 파이프는 **Ack 을 이미 보낸 뒤**라 호스트는 성공으로 봅니다.

창을 클릭하면 그때 들어옵니다. "두 번 보내면 된다" 고 느꼈던 것은, 두 번째를
보내기 전에 창을 올려 봤기 때문이었습니다.

#### 증거 — 두 번째 동기화 없이 창만 올렸습니다

```
439: [info] IRIS 링크: 씬 수신 36190776 bytes
     ... (여기서 21초 동안 아무것도 없음. Animate 가 안 돕니다)
     ... 창을 Win32 로 올림. 동기화는 보내지 않았습니다.
442: Animate: 대기 씬을 발견 — SetCurrentScene(IRIS live) 호출
443: LoadWithThreadPool: IRIS live  (라이브 이름 예 · 대기 씬 있음 · 36190776 bytes)
444: === LoadIrisb 시작
```

#### 고침

```cpp
// Sample::ShouldRenderUnfocused()
auto& bridge = iris::bridge::IrisBridge::Get();
if (bridge.HasPendingScene() || bridge.HasPendingCamera())
    return true;
```

호스트가 보낸 것이 있으면 포커스와 무관하게 프레임을 돌립니다. 더해서
설정 `render_unfocused`(기본 **켬**)가 RTXPT 의 `RenderWhenOutOfFocus` 를
몰아, 라이브 링크에서는 배경에서도 계속 그립니다 — Enscape 처럼.

확인(같은 조건: 렌더러를 다시 띄우고, 렌더러 창은 **손대지 않음**):

| | 결과 |
|---|---|
| 고치기 전 | 1/1 재현 — 21초 동안 `Animate` 줄 없음 |
| 고친 뒤 (켬) | 3/3 반영 |
| 고친 뒤 (끔) | 1/1 반영 — 대기 작업이 루프를 깨웁니다 |

끈 상태에서도 반영되는 것이 중요합니다. UI 도구설명이 그렇게 약속하므로
**그 약속이 사실이어야** 합니다.

#### 남은 구멍도 닫았습니다 — 최소화와 **거짓 성공 보고**

창을 **최소화**하면 `m_windowVisible` 이 거짓이라 Donut 은
`ShouldRenderUnfocused()` 를 묻지도 않습니다. 여기서 방향이 갈립니다.

**그 상태에서 씬을 올리지 않습니다.** 창이 0x0 이라 렌더 타깃이 0 크기로
잡힐 수 있습니다. 사용자가 일부러 내려 둔 창을 위해 GPU 를 굴리는 것도
맞지 않습니다. 복원할 때 올리는 지금 동작이 옳습니다.

문제는 반영이 미뤄지는 것이 아니라 **아무도 그 사실을 말하지 않는
것**이었습니다. 양쪽에서 말하게 했습니다.

**(1) 렌더러 — 작업 표시줄로 알립니다.**

`DeviceManager::m_callbacks.beforeFrame` 은 `RunMessageLoop` 이
**가시성과 무관하게** 매 iteration 부르는 유일한 자리입니다. 거기서
최소화 + 대기 씬이면 `glfwRequestWindowAttention()` 으로 단추만
깜빡입니다 — 포커스는 뺏지 않습니다. 대기 씬 하나에 **한 번만**
울립니다(`m_irisAttentionAsked`).

**(2) 호스트 — 단정하지 않습니다.**

`SyncAck` 은 "받았다"이지 "적용했다"가 아닙니다. 그래서 마지막 줄을
바꿨습니다:

```
이전:  렌더러 화면이 바뀌어야 합니다.          ← 우리가 알 수 없는 것
지금:  렌더러로 보냈습니다. (반영 여부는 다음 동기화 때 확인합니다)
```

렌더러는 `HelloAck` 에 상태를 실어 돌려줍니다 — `need_full` 과 같은
수법입니다:

| 칸 | 뜻 |
|---|---|
| `applied` | 지금까지 화면에 올린 씬 수 |
| `pending` | 지금 대기 중인 씬이 있는가 |
| `dropped` | 적용 전에 더 새 씬에 밀려난 수 |

Hello 는 동기화 **시작**에 보내므로 한 박자 늦게 압니다. 그 대신
기다리지 않습니다 — 전송 끝에서 확인하려면 씬 구축(0.4~2.5초)이 끝나기를
기다려야 하고 그만큼 SketchUp 이 멎습니다.

**`pending` 으로 가르는 것이 핵심입니다.** `applied` 가 안 올랐다는 것만
보면 "짓는 중" 을 실패로 말하게 되고, 그러면 이번엔 반대로 거짓말입니다.

```ruby
if same_session && pending && @sent_since_check > 0
  say '⚠ 지난번에 보낸 씬이 아직 화면에 올라가지 않았습니다.'
  say '  렌더러 창이 최소화되어 있으면 복원해 주십시오 — 그때 바로 올라갑니다.'
end
```

#### 확인 — 최소화한 채로 끝까지

렌더러를 새로 띄워 **씬을 보내기 전에** 최소화했습니다.

| 단계 | 결과 |
|---|---|
| 1차 동기화 | `씬 수신 36190776 bytes` → `새 씬이 왔는데 창이 최소화되어 있습니다` · 작업 표시줄 깜빡임 · `LoadIrisb` 없음 |
| 호스트 | `렌더러로 보냈습니다. (반영 여부는 다음 동기화 때 확인합니다)` — 단정 없음 |
| 2차 동기화 | `⚠ 지난번에 보낸 씬이 아직 화면에 올라가지 않았습니다.` |
| 창 복원 | `=== LoadIrisb 시작` — **동기화 없이** 바로 올라감 |
| 3차 동기화 | 경고 사라짐 · `렌더러가 올린 씬 1개` |

세션이 바뀐 동기화(렌더러 재시작 직후)에서는 경고하지 않습니다 — 확인했습니다.

> 곁가지: 2차의 ⚠ 가 안 보여서 "안 되는구나" 할 뻔했습니다. 경고는 Hello
> 시점이라 **동기화 출력의 맨 위**에 찍히는데, Ruby 콘솔은 끝으로 스크롤해
> 있어 가려집니다. `out/sketchup/sync_log.txt` 에서 확인했습니다. 화면에
> 안 보인다고 안 일어난 것이 아닙니다.

#### 그래도 남는 것

`applied` 가 안 올랐는데 `pending` 도 거짓인 경우 — 렌더러가 가져가서
짓는 중이거나, 읽다 실패한 것입니다. 전자는 곧 올라가므로 조용히 두고,
후자는 렌더러 쪽에 오류가 찍힙니다. 이 둘을 호스트가 가르려면 씬마다
번호를 달고 `applied_seq` 를 돌려받아야 합니다 — 지금은 그만한 값이
없다고 봅니다.

#### 곁가지 — 추적 파일이 줄을 잃고 있었습니다

고친 직후 확인에서 `Animate: 대기 씬을 발견` 줄이 사라졌습니다. 씬은
들어왔는데 그 줄만 없어서 **구조가 다른 줄 알고 한참 헤맸습니다.** 파이프
수신 스레드와 렌더 스레드가 같은 파일에 append 하다 한 줄을 잃은 것입니다.
`IrisTrace.h` 에 뮤텍스를 넣었습니다.

> 진단 도구가 조용히 줄을 잃으면, 없어진 줄이 곧 "그 분기를 안 지났다" 는
> 증거로 읽힙니다. 도구 자체가 거짓말을 하지 않아야 합니다.

### 알고 두는 것 — 면광원 재질 이름에 `|` 가 있습니다

`IRIS_AreaLight_1326.3|1.0000|...` — 키 구분자가 그대로 이름에 들어갑니다.
Windows 파일명에 못 쓰는 문자라 이 재질만 `.material.json` 저장이 실패합니다.
로그에만 남고 화면에는 영향이 없으며, 사용자가 조정할 재질도 아니라 그대로
둡니다. 모델별 이름 규칙은 다른 재질과 같게 맞춰 뒀습니다.

## 10.6 이 표를 쓰는 법

새 배선을 놓을 때 이 표에 한 줄을 더하고 **등급을 적으십시오.** `가정` 으로
적히는 줄이 생기면 그게 다음에 조용히 틀릴 자리입니다.

그리고 A/B 로 확인할 때는:

- **자동 노출을 끄십시오.** 톤매퍼가 전역 차이를 상쇄해 "닮았다/다르다"를
  만들어 냅니다. 오늘 여기에 세 번 걸렸습니다.
- **한 방향으로만 읽히는 근거**를 쓰십시오. 설계 의도처럼 어느 쪽으로도
  설명되는 것은 증거가 못 됩니다 (09번 8-g 에서 그렇게 틀렸습니다).
- **장면을 단순하게** 만드십시오. 광원 하나, 흰 바닥. 복잡한 실물 장면은
  차이를 묻어 버립니다.
