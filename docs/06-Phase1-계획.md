### 1.2 자료집의 전제 중 뒤집힌 것

Phase 0의 실질적 산출물은 "검증 통과"가 아니라 **자료집 전제 네 개가 실측과 다르다는 발견**입니다.

| 자료집 | 실측 | 근거 |
|---|---|---|
| 5장: 권장 조합 = `ReSTIR DI + NRD + DLSS` | RTXPT 기본값(DLSS-RR)이 **속도 1.4~1.6배, 품질 2~4.6배** 우세 | [04번 2·5절](04-RTXPT-실측.md) |
| 4.1: RTXDI는 "수천~수십만 광원 처리의 핵심" | 광원 **1 → 1,025** 에서 성능 변화 **+0.09%** | [04번 4절](04-RTXPT-실측.md) |
| 0장: Enscape이 시장을 가져간 이유 = 보급형에서 돌아서 | 맞다. 그런데 그 방법이 **자체 컴퓨트 BVH + 스크린스페이스**이지 RTX 스택이 아니다 | [02번 2절](02-Enscape-아키텍처-분석.md) |
| (전제 없음) | **SketchUp에는 광원 엔티티가 없다.** 태양과 앰비언트뿐 | [04번 7.4절](04-RTXPT-실측.md) |

> ⚠ 첫 항목에는 단서가 있습니다. RTXPT의 NRD가 `_SH` 변형이 아니고, NVIDIA는
> "공정 비교에는 SH 모드가 필요하다"고 밝힙니다. **"RTXPT 기본 설정 기준"으로는
> 유효하나 "NRD의 최선 대 DLSS-RR"은 아닙니다.**

## 3. Phase 1 출발점 — RTXPT 포크

두 선택지를 놓고 결정했습니다.

| | 장점 | 단점 |
|---|---|---|
| **A. RTXPT 포크** ← 채택 | Donut·NRD·Streamline·OMM·DLSS가 **이미 조립되어 있고**, 빌드·측정·실제 모델 로드까지 Phase 0에서 검증됨 | 게임용 샘플 구조. 불필요한 부분(SampleGame 등) 정리 필요. NVIDIA 고지 문구 필요 |
| B. Donut부터 직접 | 깨끗한 시작, MIT | RTXPT가 이미 해둔 통합을 다시 한다 |

**A를 택합니다.** Phase 0에서 RTXPT가 실제 SketchUp 실내 모델(400k 삼각형)을 4K 39.6 FPS로
렌더하는 것을 확인했고, **그것이 곧 Phase 1의 출발선**입니다. 자료집 19장이 "RTXPT가 가장 빠른
출발점"이라 한 것과도 일치합니다.

### 3.1 RHI — D3D12 우선

[과제 3 실측](00-진행상황.md)에서 같은 씬·설정으로 **D3D12가 Vulkan보다 1.37배
빨랐습니다**(7.2 ms vs 9.90 ms). RTXPT의 Vulkan 경로도 "수동 단계가 필요하고
SER·OMM 지원이 작업 중"입니다([04번 3절](04-RTXPT-실측.md)).

**D3D12로 시작합니다.** Windows 전용으로 확정했으므로 이식성 부담도 없습니다.
NVRHI가 양쪽을 추상화하므로 나중에 Vulkan을 여는 길은 닫히지 않습니다.

## 4. Phase 1 범위

자료집 15장의 Phase 1과 다릅니다. 차이는 전부 Phase 0 실측에서 나왔습니다.

| # | 항목 | 자료집 15장 | 우리 |
|---|---|---|---|
| 1 | 프레임 골격 | Donut/Falcor 기반 신규 | **RTXPT 포크** (이미 조립됨) |
| 2 | GI 파이프라인 | ReSTIR DI + SHaRC + NRD | **DLSS-RR 기본.** ReSTIR는 보류 |
| 3 | 씬 입력 | glTF/USD 로딩 | **자체 프로토콜 수신부.** glTF는 검증용으로만 |
| 4 | 재질 | (언급 없음) | **재질 상속** — TLAS custom index |
| 5 | 조명 | 태양·하늘·HDRI | **+ 인공조명 시스템** (SketchUp이 주지 않음) |
| 6 | 업스케일 | Streamline | 동일 (RTXPT에 포함) |
| 7 | 톤매핑·노출 | 신규 구현 | RTXPT에 이미 있음 |

### 4.1 순서

**1단계 — 포크와 정리 — ✅ 완료 (2026-09-07, `f9e0cbe`)**
- 포크 수립: `E:\iris-ext\RTXPT` 브랜치 `iris/main`, remote `upstream` = NVIDIA
- NVIDIA 고지(`NOTICE-IRIS.md`) 삽입 — 라이선스 요구사항
- **12 GB 트리를 저장소에 넣지 않고 수정분만 패치로 보존하는 구조** — [engine/README.md](../engine/README.md)
- 재현 스크립트 3종(`bootstrap`/`export`/`apply`), 왕복 바이트 동일 확인
- ⚠ `SampleGame` 제거는 **보류**. `Sample.cpp`·`SampleUI.cpp` 를 건드려 상위 병합
  충돌면만 넓히고, 자체 앱 진입점을 만들 때 어차피 사라지는 코드입니다

**2단계 — 프로토콜 수신부** — 설계 완료: **[07-프로토콜-수신부-설계.md](07-프로토콜-수신부-설계.md)**
- 전송: **명명 파이프 확정** (`\\.\pipe\iris`). SketchUp Ruby 실측 중간값 758 MB/s
  — 36 MB 씬에 47 ms, 동기화 예산의 11%
- [05번 문서](05-씬-델타-프로토콜.md)의 `Hello` / `SyncBegin·End` / `DefUpsert` /
  `InstUpsert` 최소 구현
- 현재 `.irisb` → `.glb` → 파일 로드인 경로를 **IPC 직접 수신**으로 대체
- 이 단계가 끝나면 **SketchUp에서 편집하면 렌더러가 반응**한다 — 제품의 핵심이 선다

**3단계 — 재질 상속**
- TLAS 인스턴스 custom index 기반 재질 해석
- 이것이 자체 프로토콜의 첫 실질적 이득이자, glTF로는 불가능했던 것

**4단계 — 조명 시스템** — 설계: **[09-조명-설계.md](09-조명-설계.md)**
- 태양(호스트가 주는 것) + **인공조명 배치·강도·색**(IRIS 자체 상태)
- **전제가 바뀌었습니다**: 실제 모델에 `Enscape.SpotLight` 프록시가 **29개**
  들어 있습니다. SketchUp 이 광원 엔티티를 주지 않으므로 Enscape 사용자는
  프록시 컴포넌트로 조명을 배치합니다. **그것을 읽으면 기존 Enscape 모델이
  그대로 켜지고 이주 비용이 0 이 됩니다** — 렌더링 품질이 아니라 이주 비용의 문제
- Enscape이 자체 조명 UI를 갖는 이유와 같음
- 이 단계에서 비로소 "광원이 많은 실내"가 만들어지고, **자료집 4.1의 RTXDI 전제를
  제대로 재볼 수 있게 됨**

**5단계 — 델타**
- 트랜잭션 경계 기반 증분 갱신
- 실측 기준 편집의 90%가 26 ms 이내([05번 6.4절](05-씬-델타-프로토콜.md))

### 4.2 Phase 1에서 하지 않는 것

| | 이유 |
|---|---|
| ReSTIR 통합 | 실측에서 열세. **단, NRD SH 모드 재검증 후 재고** |
| 대규모 지오메트리(클러스터 AS) | 하드웨어 경로 존재를 확인했으나, 현재 모델 규모(40만 삼각형)에서 필요 없음. 수천만 폴리곤 모델을 만나면 착수 |
