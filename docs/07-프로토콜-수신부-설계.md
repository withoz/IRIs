## 1. 결론부터 — 엔진이 이미 우리 편입니다

수신부를 설계하기 전에 Donut의 씬 표현을 읽었습니다.
**우리가 만들려던 것의 상당 부분이 이미 있습니다.**

| 우리 프로토콜 | Donut/RTXPT에 이미 있는 것 |
|---|---|
| `DefUpsert` (정의 = 지오메트리) | `MeshInfo` + `BufferGroup` + `SceneGraph::GetMeshes()` |
| `InstUpsert` (인스턴스 = 배치) | `MeshInstance` + `SceneGraphNode` + `Attach`/`Detach` |
| 재질 | `Material` + `ResourceTracker<Material>` |
| 델타 감지 | **`HasPendingStructureChanges()` / `HasPendingTransformChanges()`** |
| 증분 갱신 | **`RefreshSceneGraph()` → `RefreshBuffers()`** |
| 변경분만 GPU 업로드 | **`CreateMeshBuffers()` 가 이미 기존 버퍼를 건너뜁니다** |

`Scene::CreateMeshBuffers` (`External/Donut/src/engine/Scene.cpp:821`):

```cpp
for (const auto& mesh : m_SceneGraph->GetMeshes()) {
    auto buffers = mesh->buffers;
    if (!buffers) continue;
    if (!buffers->indexData.empty() && !buffers->indexBuffer) { ... }   // ← 이미 있으면 건너뜀
    if (!buffers->vertexBuffer) { ... }
}
```

즉 **씬 그래프에 새 `MeshInfo` 를 붙이고 `RefreshBuffers` 를 부르면 그것만
GPU로 올라갑니다.** 델타 프로토콜(5단계)이 엔진을 개조해야 하는 일이 아닙니다.

> 이것은 [06번 문서](06-Phase1-계획.md)가 세운 5단계 순서를 뒷받침합니다.
> 2단계(전체 동기화)를 제대로 만들면 5단계(델타)는 대부분 따라옵니다.

## 2. 반드시 알아야 할 제약

### 2.1 CPU 데이터는 업로드 후 버려집니다

`CreateMeshBuffers` 는 업로드 직후 CPU 벡터를 비웁니다.

```cpp
commandList->writeBuffer(buffers->indexBuffer, buffers->indexData.data(), ...);
std::vector<uint32_t>().swap(buffers->indexData);     // ← 해제
```

**귀결**: 이미 올라간 정의의 지오메트리가 바뀌면 **그 자리에서 고칠 수 없습니다.**
`MeshInfo` 를 통째로 새로 만들어 교체해야 합니다.

우리 모델에서는 문제가 되지 않습니다. **정의가 바뀌었다는 것은 지오메트리가
새로 나왔다는 뜻**이고([05번 6절](05-씬-델타-프로토콜.md)), 프로브도 그 정의를
통째로 다시 추출합니다. 다만 *"정점 몇 개만 갱신"* 같은 최적화 여지는 없다는 뜻이며,
이는 5단계에서 기억해야 합니다.

### 2.2 법선은 패킹해서 넣어야 합니다

`BufferGroup::normalData` 는 `std::vector<uint32_t>` 입니다 — float3가 아닙니다.
Donut이 `vectorToSnorm8()` 로 압축해 넣습니다
(`External/Donut/src/engine/GltfImporter.cpp:1282`).

우리 `.irisb` 는 f32×3 으로 보내므로 **수신부에서 같은 함수로 패킹**합니다.
탄젠트도 같습니다.

### 2.3 씬 로딩은 `ExtendedScene` 을 거칩니다

RTXPT는 `donut::engine::Scene` 을 `ExtendedScene` 으로 감싸고
`ExtendedSceneTypeFactory` 를 씁니다 (`Rtxpt/Sample.cpp:449`).
수신부도 **반드시 이 팩토리로 객체를 만들어야** RTXPT의 확장 재질·설정 노드가
정상 동작합니다. `new MeshInfo` 같은 직접 생성은 금지입니다.

## 3. 구조

경계를 디렉터리로 드러냅니다 — 라이선스 측면에서도 그래야 합니다
([engine/README.md](../engine/README.md)).

```
E:\IRIS\src\                     ← IRIS 고유 코드. 저장소에 그대로 들어감
  iris/
    protocol/
      IrisbReader.h/.cpp         .irisb 파싱 (헤더 + JSON 매니페스트 + 블롭)
      PipeServer.h/.cpp          명명 파이프 수신 (\\.\pipe\iris)
      Messages.h                 Hello / SyncBegin / DefUpsert / InstUpsert / SyncEnd
    bridge/
      SceneBuilder.h/.cpp        수신 데이터 → Donut SceneGraph
      IrisBridge.h/.cpp          수명주기 + 프레임 틱

engine/patches/                  ← 엔진 쪽 훅만. 최소로 유지
```

### 3.1 엔진 훅 — 세 지점뿐

엔진 수정을 최소로 두는 것이 상위 병합 비용을 정합니다.
`Sample.cpp` 에 다음 세 줄만 넣습니다.

| 지점 | 호출 |
|---|---|
| 초기화 | `m_irisBridge = IrisBridge::Create(GetDevice(), m_scene, ...)` |
| 프레임 갱신 | `m_irisBridge->Tick(commandList, GetFrameIndex())` |
| 종료 | `m_irisBridge.reset()` |

나머지는 전부 `src/` 안에 있습니다.

## 4. 흐름

```
SketchUp (Ruby)                     IRIS 렌더러
──────────────                      ───────────
                                    PipeServer 대기 (\\.\pipe\iris)
연결                        ──────► 수락
Hello{ver, model, units}    ──────►
                            ◄────── HelloAck{ver, 수용/거부}
SyncBegin{seq}              ──────►
.irisb 블롭 (36 MB)         ──────► IrisbReader 파싱
                                    SceneBuilder → MeshInfo/Material/MeshInstance
SyncEnd{seq}                ──────►
                                    RefreshSceneGraph + RefreshBuffers
                            ◄────── SyncAck{seq, 처리 ms}
```

### 4.1 스레드 규칙

파이프 수신은 **별도 스레드**에서 돕니다. 렌더 스레드를 36 MB 읽기로 막으면
프레임이 끊깁니다.

- 수신 스레드: 파이프 읽기 → `.irisb` 파싱 → **CPU측 중간 표현**까지 만든다
- 렌더 스레드: `Tick()` 에서 완성된 중간 표현을 씬 그래프에 반영하고 GPU 업로드

nvrhi 객체 생성과 `commandList` 사용은 **렌더 스레드 전용**입니다.
경계는 완성된 중간 표현 하나를 넘기는 큐입니다.

## 5. 단계 나누기

2단계를 한 번에 다 만들지 않습니다. 각 칸이 **눈으로 확인 가능한 상태**입니다.

| # | 만드는 것 | 확인 방법 |
|---|---|---|
| **2a ✅** | `IrisbReader` — `.irisb` 파싱 | **완료 (2026-09-08)**. 아래 5.1 |
| 2b | `SceneBuilder` — 파싱 결과 → `SceneGraph` | **`.irisb` 파일을 직접 열어 렌더**. glTF 변환 단계가 사라진다 |
| 2c | `PipeServer` + `IrisBridge` | SketchUp에서 보내면 화면이 바뀐다 |
| 2d | Ruby 송신부 (`iris_probe.rb` 확장) | 왕복 완성 |

**2b가 가장 큰 이득입니다.** 지금은
`.irisb` → `iris_json_to_gltf.py` → `.glb` → Donut glTF 로더인데,
2b가 끝나면 **`.irisb` → Donut SceneGraph** 로 직행합니다.
파이썬 변환기와 glTF의 제약([05번 2절](05-씬-델타-프로토콜.md))이 함께 사라집니다.

### 5.1 2a 완료 — `IrisbReader` (2026-09-08)

골프존 실내 모델(36 MB)로 잰 결과입니다.

| | 값 |
|---|---|
| 읽기 시간 | **55.3 ms** (파일 I/O + JSON 580 KB 파싱 + 인덱스 120만 개 전수 검증) |
| 시험 | **22/22 통과** |

**현재 경로와의 비교**

| | 시간 | 중간 산출물 |
|---|---|---|
| 지금: `iris_json_to_gltf.py` | **1,121 ms** | `.glb` **85 MB** 를 디스크에 쓰고 Donut 이 다시 파싱 |
| 2a 리더 | **55.3 ms** | 없음 (메모리) |

**20배**이고, 85 MB 쓰기·읽기가 통째로 사라집니다.
동기화 예산 434 ms 안에서 파싱이 차지하는 몫이 13% 로 들어옵니다.

**설계상 지킨 것**

- **엔진 비의존.** `Donut`/`nvrhi` 타입이 헤더에 없어 단독 빌드·시험이 됩니다
- **입력을 신뢰하지 않습니다.** 파이프 너머에서 오는 데이터이므로
  헤더·선언 크기·모든 `{off,count}`·오프셋 정렬·인덱스 범위를 전부 검사합니다.
  검사를 빠뜨리면 잘못된 인덱스가 BLAS 빌드로 들어가 GPU 가 죽습니다
- **`strict` 옵션.** 라이브 링크 중에는 씬 전체를 버리는 것보다 문제 버킷만
  버리고 계속하는 편이 나은 경우가 있습니다
- 검증한 오류 경로: 짧은 입력 · 잘못된 MAGIC · 모르는 버전 · 잘린 파일 ·
  블롭 범위 밖 참조

> 기대값은 **리더가 아니라 Python 으로 따로 세어** 얻었습니다.
> 리더가 스스로를 검증하게 두면 시험이 아닙니다.

## 6. 열린 문제

| | |
|---|---|
| 재질 상속 | 3단계 과제. 2b에서는 정의 기본 재질만 씁니다 |
| 텍스처 전달 | 현재는 파일 경로. 파이프로 바이트를 보낼지, 경로를 넘길지 미정 — 같은 머신이므로 경로가 단순합니다 |
| Z-up → Y-up | 현재 변환기가 루트 노드 회전으로 처리. 수신부도 같게 합니다 |
| 좌표 단위 | 프로브가 이미 m 로 내보냅니다 |
