## 1. 결론부터 — 엔진이 이미 우리 편입니다

수신부를 설계하기 전에 Donut의 씬 표현을 읽었습니다.
**우리가 만들려던 것의 상당 부분이 이미 있습니다.**

| 우리 프로토콜 | Donut/RTXPT에 이미 있는 것 |
|---|---|
| `DefUpsert` (정의 = 지오메트리) | `MeshInfo` + `BufferGroup` + `SceneGraph::GetMeshes()` |
| `InstUpsert` (인스턴스 = 배치) | `MeshInstance` + `SceneGraphNode` + `Attach`/`Detach` |
| 재질 | `Material` + `ResourceTracker<Material>` |
| 델타 감지 | **`HasPendingStructureChanges()` / `HasPendingTransformChanges()`** |
| 증분 갱신 | **`RefreshSceneGraph()` → `RefreshBuffers()`** |
| 변경분만 GPU 업로드 | **`CreateMeshBuffers()` 가 이미 기존 버퍼를 건너뜁니다** |

`Scene::CreateMeshBuffers` (`External/Donut/src/engine/Scene.cpp:821`):

```cpp
for (const auto& mesh : m_SceneGraph->GetMeshes()) {
    auto buffers = mesh->buffers;
    if (!buffers) continue;
    if (!buffers->indexData.empty() && !buffers->indexBuffer) { ... }   // ← 이미 있으면 건너뜀
    if (!buffers->vertexBuffer) { ... }
}
```

즉 **씬 그래프에 새 `MeshInfo` 를 붙이고 `RefreshBuffers` 를 부르면 그것만
GPU로 올라갑니다.** 델타 프로토콜(5단계)이 엔진을 개조해야 하는 일이 아닙니다.

> 이것은 [06번 문서](06-Phase1-계획.md)가 세운 5단계 순서를 뒷받침합니다.
> 2단계(전체 동기화)를 제대로 만들면 5단계(델타)는 대부분 따라옵니다.

## 2. 반드시 알아야 할 제약

### 2.1 CPU 데이터는 업로드 후 버려집니다

`CreateMeshBuffers` 는 업로드 직후 CPU 벡터를 비웁니다.

```cpp
commandList->writeBuffer(buffers->indexBuffer, buffers->indexData.data(), ...);
std::vector<uint32_t>().swap(buffers->indexData);     // ← 해제
```

**귀결**: 이미 올라간 정의의 지오메트리가 바뀌면 **그 자리에서 고칠 수 없습니다.**
`MeshInfo` 를 통째로 새로 만들어 교체해야 합니다.

우리 모델에서는 문제가 되지 않습니다. **정의가 바뀌었다는 것은 지오메트리가
새로 나왔다는 뜻**이고([05번 6절](05-씬-델타-프로토콜.md)), 프로브도 그 정의를
통째로 다시 추출합니다. 다만 *"정점 몇 개만 갱신"* 같은 최적화 여지는 없다는 뜻이며,
이는 5단계에서 기억해야 합니다.

### 2.2 법선은 패킹해서 넣어야 합니다

`BufferGroup::normalData` 는 `std::vector<uint32_t>` 입니다 — float3가 아닙니다.
Donut이 `vectorToSnorm8()` 로 압축해 넣습니다
(`External/Donut/src/engine/GltfImporter.cpp:1282`).

우리 `.irisb` 는 f32×3 으로 보내므로 **수신부에서 같은 함수로 패킹**합니다.
탄젠트도 같습니다.

### 2.3 씬 로딩은 `ExtendedScene` 을 거칩니다

RTXPT는 `donut::engine::Scene` 을 `ExtendedScene` 으로 감싸고
`ExtendedSceneTypeFactory` 를 씁니다 (`Rtxpt/Sample.cpp:449`).
수신부도 **반드시 이 팩토리로 객체를 만들어야** RTXPT의 확장 재질·설정 노드가
정상 동작합니다. `new MeshInfo` 같은 직접 생성은 금지입니다.

경계를 디렉터리로 드러냅니다 — 라이선스 측면에서도 그래야 합니다
([engine/README.md](../engine/README.md)).

```

  iris/
    protocol/
      IrisbReader.h/.cpp         .irisb 파싱 (헤더 + JSON 매니페스트 + 블롭)
      Wire.h                     프레임 형식과 메시지 종류
      PipeServer.h/.cpp          명명 파이프 수신 (별도 스레드)
    bridge/                      Donut 을 아는 계층
      SceneBuilder.h/.cpp        파싱 결과 → Donut SceneGraph
      IrisBridge.h/.cpp          파이프 서버 수명 + 스레드 경계

  test_irisb_reader.cpp          22/22
  test_pipe_server.cpp           22/22

engine/patches/                  ← 엔진 쪽 훅만. 패치 3개 / 28 KB
```

> `protocol/` 은 **엔진을 모릅니다.** 단독으로 빌드하고 시험합니다.

### 3.1 엔진 훅 — 실제로 넣은 것

| 지점 | 하는 일 |
|---|---|
| `Sample::Init` | `IrisBridge` 시작 + 씬 목록에 `"IRIS live"` 추가 |
| `Sample::Animate` | 대기 중인 씬이 있으면 `SetCurrentScene("IRIS live", force)` |
| `Sample::LoadScene` | `ExtendedScene` → `IrisScene` |
| `Rtxpt/Iris/IrisScene` | `.irisb`·라이브 씬만 가로채고 나머지는 상위로 넘김 |

**`Tick()` 은 만들지 않았습니다.** 엔진의 씬 전환 경로(`SetCurrentScene`)를
그대로 부르는 편이 낫습니다 — `SceneLoaded` 가 BLAS 재빌드·카메라·베이커를
전부 다시 돌립니다. 직접 구현했다면 빠뜨렸을 것들입니다.

나머지는 전부 `src/` 안에 있습니다.

## 4. 흐름

```
SketchUp (Ruby)                     IRIS 렌더러
──────────────                      ───────────
                                    PipeServer 대기 (\\.\pipe\iris)
연결                        ──────► 수락
Hello{ver, model, units}    ──────►
                            ◄────── HelloAck{ver, 수용/거부}
SyncBegin{seq}              ──────►
.irisb 블롭 (36 MB)         ──────► IrisbReader 파싱
                                    SceneBuilder → MeshInfo/Material/MeshInstance
SyncEnd{seq}                ──────►
                                    RefreshSceneGraph + RefreshBuffers
                            ◄────── SyncAck{seq, 처리 ms}
```

### 4.1 스레드 규칙

파이프 수신은 **별도 스레드**에서 돕니다. 렌더 스레드를 36 MB 읽기로 막으면
프레임이 끊깁니다.

- 수신 스레드: 파이프 읽기 → `.irisb` 파싱 → **CPU측 중간 표현**까지 만든다
- 렌더 스레드: `Tick()` 에서 완성된 중간 표현을 씬 그래프에 반영하고 GPU 업로드

nvrhi 객체 생성과 `commandList` 사용은 **렌더 스레드 전용**입니다.
경계는 완성된 중간 표현 하나를 넘기는 큐입니다.

### 5.1 2a 완료 — `IrisbReader` (2026-09-08)

골프존 실내 모델(36 MB)로 잰 결과입니다.

| | 값 |
|---|---|
| 읽기 시간 | **55.3 ms** (파일 I/O + JSON 580 KB 파싱 + 인덱스 120만 개 전수 검증) |
| 시험 | **22/22 통과** |

**현재 경로와의 비교**

| | 시간 | 중간 산출물 |
|---|---|---|
| 지금: `iris_json_to_gltf.py` | **1,121 ms** | `.glb` **85 MB** 를 디스크에 쓰고 Donut 이 다시 파싱 |
| 2a 리더 | **55.3 ms** | 없음 (메모리) |

**20배**이고, 85 MB 쓰기·읽기가 통째로 사라집니다.
동기화 예산 434 ms 안에서 파싱이 차지하는 몫이 13% 로 들어옵니다.

**설계상 지킨 것**

- **엔진 비의존.** `Donut`/`nvrhi` 타입이 헤더에 없어 단독 빌드·시험이 됩니다
- **입력을 신뢰하지 않습니다.** 파이프 너머에서 오는 데이터이므로
  헤더·선언 크기·모든 `{off,count}`·오프셋 정렬·인덱스 범위를 전부 검사합니다.
  검사를 빠뜨리면 잘못된 인덱스가 BLAS 빌드로 들어가 GPU 가 죽습니다
- **`strict` 옵션.** 라이브 링크 중에는 씬 전체를 버리는 것보다 문제 버킷만
  버리고 계속하는 편이 나은 경우가 있습니다
- 검증한 오류 경로: 짧은 입력 · 잘못된 MAGIC · 모르는 버전 · 잘린 파일 ·
  블롭 범위 밖 참조

> 기대값은 **리더가 아니라 Python 으로 따로 세어** 얻었습니다.
> 리더가 스스로를 검증하게 두면 시험이 아닙니다.

#### 5.2.1 여기서 잡은 문제 다섯 가지

이 단계에서 나온 것들이 전부 **문서에 남길 값어치가 있는 함정**이었습니다.

**① UTF-8 문자열을 `std::filesystem::path` 로 (치명적)**

MSVC 에서 `std::filesystem::path(std::string)` 은 **현재 ANSI 코드페이지**로
해석합니다. 한국어 환경(CP949)에 UTF-8 바이트를 넘기면 되돌릴 수 없는 문자가
생기고, 나중에 `path::string()` 이 던지는 예외가 잡히지 않아
**`std::terminate` → `abort`(0xC0000409)** 로 죽습니다. **이유가 아무것도
남지 않습니다.** 텍스처 경로에 한글 폴더명이 있어서 걸렸습니다.
→ `Utf8Path()` 로 UTF-8 을 명시해 변환.

**② UTF-8 이름을 `Material::name` 에 (같은 뿌리, 더 찾기 어려움)**

Donut/RTXPT 는 이름으로 **파일 경로를 만듭니다**
(`MaterialsBaker::GetMaterialStoragePath`, `SceneGraphNode::GetPath`).
UTF-8 바이트를 넣으면 ①과 같은 경로로 죽습니다.
→ `ToNativeNarrow()` 로 시스템 ANSI 인코딩으로 변환. CP949 에서 한글은
그대로 보존되고 표현 못 하는 문자만 `_` 가 됩니다.

> **원인을 찾은 방법**: `std::set_terminate` 핸들러를 걸어 잡히지 않은 예외의
> `what()` 을 파일로 건졌습니다 — *"No mapping for the Unicode character exists
> in the target multi-byte code page."* 이것 없이는 못 찾았습니다.
> 진단 장치는 `IRIS_TRACE_LOG` 환경변수로 켭니다.

**③ 광원이 없어 화면이 완전히 검음**

**SketchUp 에는 광원 엔티티가 없습니다**([04번 7.4절](04-RTXPT-실측.md)).
`.irisb` 에도 없습니다. 패스트레이서에 광원을 하나도 주지 않으면 결과는
당연히 검정입니다.
→ 기본 환경광(하늘 HDRI)을 넣습니다. 건축 렌더러가 모델을 열었을 때 무언가
보이는 것이 옳은 기본값이기도 합니다. **본격적인 조명은 Phase 1 4단계입니다.**

**④ 초기 카메라가 어두운 시점**

RTXPT 는 **마지막 카메라**를 초기 시점으로 씁니다(`cameras.back()`).
SketchUp 장면 4개 중 마지막(Scene 3)이 벽을 마주보는 어두운 자리여서
화면이 검게 나왔습니다. **수동으로 같은 좌표를 넘겨도 검게 나왔으므로
우리 카메라 코드는 정상이었습니다.**
→ SketchUp 의 **'현재 뷰'를 맨 뒤에 한 번 더** 답니다. 사용자가 방금 보던
화면이 렌더러의 첫 화면이 되는 것이 옳습니다.

**⑤ `/W4 /WX` 가 서드파티 헤더에서 터짐**

Donut 의 `SceneGraph.h` 에서 C4100 이 나 빌드가 멈췄습니다.
→ `/external:anglebrackets /external:W0`. IRIS 헤더는 따옴표, 서드파티는
꺾쇠로 포함하므로 경계가 자동으로 갈립니다.

#### 5.2.2 구조상 지킨 것

- **엔진 변경은 패치 2개 / 16 KB** 뿐입니다. 실제 로직은 전부 `src/` 에 있습니다
- `IrisScene` 은 `.irisb` 만 가로채고 **나머지는 전부 상위 구현으로 넘깁니다** —
  기존 RTXPT 씬이 그대로 동작합니다(회귀 확인 완료)
- `SceneBuilder` 는 **RTXPT 타입을 모릅니다.** `EnvironmentLight` 같은 RTXPT
  전용 타입도 `SceneTypeFactory::CreateLeaf("이름")` 으로만 만듭니다
- 변환행렬은 **glTF 임포터와 완전히 같은 경로**로 넣습니다. 규약을 새로
  해석하지 않는 것이 목적입니다 — 틀리면 씬 전체가 전치됩니다

#### 5.2.3 전단(shear) 실측

Donut 의 `SceneGraphNode` 는 변환을 **TRS(이동·쿼터니언·스케일)** 로 저장하므로
전단을 표현할 수 없습니다. 실제 모델에서 문제가 되는지 쟀습니다.

| | 인스턴스 1,155개 중 |
|---|---|
| 전단 지표 > 1e-2 | **0** |
| 전단 지표 > 1e-4 | 1 |
| 최댓값 | 1.6e-3 (부동소수점 잡음 수준) |
| 비균일 스케일 | 201 (17%) — `decomposeAffine` 이 정확히 처리 |

**전단은 실질적으로 없습니다.** 기존 glTF 경로도 같은 손실을 갖고 있었고,
새 경로가 더 나빠지지 않았습니다.

## 7. 2c 완료 — 라이브 링크 (2026-09-08)

**실행 중인 렌더러가 파이프로 받은 씬으로 갈아탑니다.** bistro 를 렌더하던
RTXPT 에 골프존 모델을 보내니 그대로 교체됐습니다. 파일도, 재시작도 없습니다.

### 7.1 와이어 형식

```
[type u32][flags u32][payloadLen u64][payload]
```

| 종류 | 방향 | 페이로드 |
|---|---|---|
| `Hello` | 호스트 → 렌더러 | JSON `{protocol, app, model, unit, up_axis, texture_base}` |
| `HelloAck` | 렌더러 → 호스트 | JSON `{protocol, accepted, renderer, reason}` |
| `SyncBegin` | 호스트 → 렌더러 | JSON `{seq}` |
| `SceneBlob` | 호스트 → 렌더러 | `.irisb` 바이트 그대로 |
| `SyncEnd` | 호스트 → 렌더러 | JSON `{seq}` |
| `SyncAck` | 렌더러 → 호스트 | JSON `{seq, ok, ms, error}` |
| `Bye` | 양방향 | 없음 |

**채널을 둘로 나누지 않았습니다.** [05번 3절](05-씬-델타-프로토콜.md)은 제어와
벌크를 나눌 것을 고려했지만, 실측에서 파이프가 758 MB/s 였고 36 MB 씬이 47 ms
였습니다. 순서가 보장되는 스트림 하나로 충분하고, 두 채널의 순서를 맞추는
복잡함을 살 이유가 없습니다.

`SceneBlob` 의 `flags` 에 `Partial` 비트를 예약해 두었습니다. **`.irisb` 가
바뀐 정의만 담을 수 있으므로 그것이 곧 델타 전송 수단이 됩니다** — 5단계에서
새 메시지를 만들 필요가 없습니다. 지금은 명시적으로 거절합니다.

### 7.2 실측

| | |
|---|---|
| 파이프 왕복 (C++ 클라이언트, 36 MB) | **47.4 ms = 725 MB/s** — 수신측 전체 파싱 포함 |
| 라이브 교체 — 읽기 | **29.1 ms** (메모리. 파일 경로는 54 ms) |
| 라이브 교체 — 씬 구축 | 649 ms (텍스처 디코드가 대부분) |
| 시험 | **22/22 통과** |

### 7.3 구조

```
SketchUp (Ruby)                 IRIS 렌더러
  파이프 클라이언트  ──────────▶  PipeServer   (수신 스레드)
                                     │  .irisb 바이트
                                     ▼
                                  IrisBridge   (프로세스 수명, 뮤텍스)
                                     │  HasPendingScene / TakePendingScene
                                     ▼
                                  Sample::Animate  (렌더 스레드)
                                     │  SetCurrentScene("IRIS live", force)
                                     ▼
                                  IrisScene → SceneBuilder → SceneGraph
```

**`IrisBridge` 가 프로세스 수명 동안 서버를 듭니다.** 씬은 로드할 때마다 새로
만들어지므로 거기에 서버를 두면 씬이 바뀔 때마다 연결이 끊깁니다.

**엔진의 씬 전환 경로를 그대로 재사용합니다.** `SetCurrentScene(가상이름, force)`
를 부르면 `SceneLoaded` 가 BLAS 재빌드·카메라·베이커를 전부 다시 돌립니다.
직접 구현했다면 빠뜨렸을 것들입니다.

### 7.4 지킨 것

- **밀린 씬은 버리고 최신으로 갈아탑니다.** 큐에 쌓으면 편집이 빠를 때 지연만
  늘어납니다. 라이브 링크에서 중요한 것은 "최신 상태"이지 "모든 중간 상태"가 아닙니다
- **페이로드 한도 512 MB.** 신뢰하지 않는 입력이 길이를 크게 선언해 메모리를
  고갈시키는 것을 막습니다
- **파이프 인스턴스 4개.** 1개로 두면 낡은 인스턴스 하나가 이름을 잡았을 때
  생성도 연결도 전부 `EACCES` 가 되고, "없음"이 아니라 "거부"라 원인을 짚기
  어렵습니다 — 실제로 헤맸습니다
- **프로토콜 버전 불일치는 거절합니다.** 호스트 확장과 렌더러가 따로 배포될 수
  있으므로([05번 9절](05-씬-델타-프로토콜.md)) 조용히 진행하면 안 됩니다
- **모르는 프레임 종류는 건너뜁니다.** 필드 추가가 하위 호환이 되도록 하는 것과
  같은 이유입니다

검증한 오류 경로: `Hello` 없는 `SceneBlob` · 한도 초과 선언 · 깨진 `.irisb` ·
버전 불일치. 전부 보고하고 연결을 닫으며, 이후 재연결이 정상 동작합니다.

### 7.5 텍스처 기준 경로

라이브 씬은 **파일로 존재하지 않으므로** "씬 파일 옆"이라는 기준을 쓸 수
없습니다. 호스트가 `Hello` 의 `texture_base` 로 알려줍니다.
같은 머신이므로 파일 경로를 주고받는 것이 단순합니다 — 05번 문서가 열어 둔
항목이며, 원격 구성이 생기면 바이트 전송을 다시 봅니다.

### 7.6 참조 구현

[`tools/rtxpt/iris_send.py`](../tools/rtxpt/iris_send.py) 가 호스트 쪽을
그대로 구현합니다. **2d 의 Ruby 송신부는 이것을 옮기면 됩니다.**
파이프를 일반 파일 열기로 여는 것까지 같습니다.

## 8. 2d 완료 — 왕복이 섰습니다 (2026-09-08)

**SketchUp 에서 편집하면 렌더러 화면이 따라옵니다.**
[`tools/sketchup/iris_link.rb`](../tools/sketchup/iris_link.rb) 가 호스트 쪽입니다.

```ruby
IRIS::Link.sync       # 한 번 보내기
IRIS::Link.auto       # 편집 감시 + 자동 전송
IRIS::Link.auto_stop
```

`auto` 는 정의 캐시의 옵저버가 무효화한 항목이 있을 때만 동기화합니다.
델타 전송은 아직 아니지만(5단계) **추출은 바뀐 정의만** 합니다.

### 8.1 여기서 잡은 것 — 텍스처가 매번 다시 디코드되고 있었습니다

자동 모드를 켜 두고 로그를 보니 **동기화마다 같은 텍스처 40장을 다시
디코드**하고 있었습니다. 79회 동기화에 디코드 로그가 3,318줄이었습니다.

원인은 `ApplicationBase::BeginLoadingScene` 이 씬을 로드할 때마다
`m_TextureCache->Reset()` 을 부르는 것입니다. **다른 씬으로 바꿀 때는
맞는 동작**이지만, 라이브 갱신에서는 곧바로 다시 읽을 것을 버립니다.

`Reset()` 은 맵만 비웁니다. **`shared_ptr` 을 들고 있으면 텍스처도 GPU
자원도 살아남습니다.** `IrisBridge` 가 경로를 키로 들고 `SceneBuilder` 에
로더로 끼워 넣었습니다.

| | 구축 시간 | 텍스처 단계 |
|---|---|---|
| 첫 로드 | 661.3 ms | 638 ms |
| **이후 모든 갱신** | **17.5 ~ 21.8 ms** | **0 ms** |

**33배**입니다. 텍스처 디코드는 이제 딱 한 번만 일어납니다.

> 이 문제는 **자동 모드를 실제로 돌려 보기 전에는 보이지 않았습니다.**
> 한 번 로드하는 시험에서는 "텍스처 디코드가 96%"가 정상으로 보였습니다.

### 8.2 라이브 갱신 지연 (렌더러 쪽)

| 단계 | 시간 |
|---|---|
| 파이프 수신 + `.irisb` 파싱 | 27 ms |
| 씬 그래프 구축 | **20 ms** |
| **합계** | **약 47 ms** |

첫 로드만 텍스처 디코드 때문에 660 ms 이고, 이후 편집은 47 ms 입니다.
