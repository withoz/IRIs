## 1. 전제가 바뀌었습니다

지금까지 문서에 이렇게 적어 왔습니다.

> **SketchUp 에는 광원 엔티티가 없습니다.** 태양과 앰비언트뿐입니다.
> ([04번 7.4절](04-RTXPT-실측.md))

**그건 여전히 사실입니다.** 그런데 실제 프로젝트 모델을 열어 보니 다른 것이
있었습니다. SketchUp 이 광원을 주지 않으므로 Enscape 는 **프록시 컴포넌트**로
조명을 표현하고, 실제 설정은 **속성 사전에 XML 로** 남깁니다.

| 정의 | xsi:type | 인스턴스 |
|---|---|---|
| `Enscape.SpotLight#1`~`#4` | `SketchupIesLight` | 29 |
| `Enscape.PointLight` | `SketchupPointLight` | 18 |
| `Enscape.RectangularLight` | `SketchupRectangularLight` | 4 |
| `Enscape.LinearLight` | `SketchupLinearLight` | 1 |
| **합계** | | **52** |

**사용자는 이미 조명을 배치해 두었습니다.**

> 주의 — 이름에 속지 마십시오. `Ceiling light (Flyingarchs)` 는 인스턴스가 29개라
> 조명처럼 보이지만 **조명기구 모델**입니다. 실제 빛은 그 기구에 칠해진
> **자체발광 재질**에서 나옵니다(5.3절). 판별 기준은 이름이 아니라
> `Enscape.Light` 사전의 유무입니다.

---

## 2. 이것이 왜 중요한가

**기존 Enscape 사용자의 모델이 그대로 켜집니다.**

IRIS 의 경쟁 상대는 Enscape 입니다([02번 문서](02-Enscape-아키텍처-분석.md)).
그 사용자가 IRIS 로 옮기려면 **조명을 전부 다시 배치**해야 한다면, 그것만으로
이주가 막힙니다. 실내 프로젝트 하나에 조명이 수십 개입니다.

프록시를 해석하면 그 비용이 **0** 이 됩니다. 파일을 열면 조명이 이미 켜져 있습니다.

> 이것은 렌더링 품질이 아니라 **이주 비용**의 문제이고,
> [자료집 0장](01-실시간렌더러-오픈소스-자료집.md)이 말한
> *"제품의 해자는 렌더러가 아니다"* 와 같은 줄기입니다.

## 3. 실측한 스키마

`tools/sketchup/iris_dump_attrs.rb` 로 원문을 떴습니다. 조사 도구가 값을 100자에서
자르기 때문에 XML 은 전용 도구가 필요했습니다.

### 3.1 조명 — `Enscape.Light` / `LightData`

```xml
<SketchupLight xsi:type="SketchupIesLight">
  <Luminosity>83860.4024510768</Luminosity>
  <OriginalIesFile>E:\D. 스케치업 자료\ies_data\Bega.8331WIDE.IES</OriginalIesFile>
  <IesData>[base64 로 인코딩된 IES 측광 데이터 전체]</IesData>
</SketchupLight>
```

| 타입 | 필드 |
|---|---|
| `SketchupIesLight` | `Luminosity` · `OriginalIesFile` · `IesData`(base64) |
| `SketchupPointLight` | `Luminosity` · `LightSourceRadius` |
| `SketchupRectangularLight` | `Luminosity` · `Width` · `Length` |
| `SketchupLinearLight` | `Luminosity` · `Length` |

**위치도 방향도 원뿔각도 없습니다.**

- 위치·방향 → 프록시 **인스턴스의 변환**에서 나옵니다. 씬 그래프가 합성하므로
  노드에 광원 잎을 달기만 하면 됩니다. 다만 **어느 축이 정면인지**는 실측해야
  합니다 — 4.2절
- 원뿔각 → **IES 배광**에서 유도합니다(3.3절)
- 색 → 기본값(흰색)이면 아예 적지 않습니다

`Width`·`Length`·`LightSourceRadius` 는 SketchUp 내부 단위인 **인치**입니다
(118.11 인치 = 정확히 3.0 m).

### 3.2 Luminosity 의 단위 — 추론입니다

문서가 아니라 값에서 역추론했습니다. 정직하게 적어 둡니다.

| 광원 | 값 | 루멘으로 읽으면 |
|---|---|---|
| LinearLight | **1000**(정확) | 30 cm 스트립 1000 lm |
| PointLight | 989.28 | 백열 60~75 W 급 |
| RectangularLight | 2831.65 | 3.0 × 2.45 m 패널 |
| IesLight | 83860.4 | 파일 선언 8500 lm 의 9.87배 |

1000 이 정확히 떨어지는 것과 989 lm 이 물리적으로 타당한 것을 근거로
**루멘(lm)** 으로 봅니다. IES 만 크지만, Enscape 의 세기 슬라이더를 올려 잡는 것은
흔한 작업 방식입니다.

틀렸다면 `IRIS::Enscape.lumen_scale` **한 값으로 교정**됩니다.

### 3.3 IES 를 원뿔각으로

RTXPT 는 IES 프로파일을 **아직 지원하지 않습니다.** `LightsBaker.cpp` 에 주석
처리된 예시가 있고 셰이더의 `evaluateIesProfile` 은 비어 있습니다.

그래서 텍스처로 넘기는 대신 배광을 파싱해 원뿔각을 유도합니다 —
50%에서 내부 원뿔(빔각), 10%에서 외부 원뿔(필드각). 조명업계의 정의 그대로입니다.

이 모델의 Bega 8331WIDE 실측:

| | |
|---|---|
| 파일 구조 | 세로각 19 × 가로각 19 = 361 값 · 파싱 후 잔여 0 |
| 유도한 빔각 | 반각 **29.83°** (전각 59.7°) |
| 유도한 필드각 | 반각 **54.25°** (전각 108.5°) — "WIDE" 와 맞습니다 |
| 축상 광도 | 5968.7 cd |
| **구면 적분 광속** | **5088 lm** (선언 램프 광속 8500 lm 대비 효율 59.9%) |

효율 59.9%는 매입 다운라이트의 전형값입니다. **파서가 맞다는 강한 방증**입니다.

> 대칭 배수를 빠뜨리면 안 됩니다. IES 는 대칭이면 일부만 적습니다 —
> 가로각이 0~90 이면 사분 대칭이라 4를 곱해야 전체 광속이 됩니다.
> 빠뜨리면 광속이 4분의 1이 되어 조명이 4배 밝아집니다.

### 3.4 루멘 → 칸델라

Donut 의 `SpotLight::intensity` 는 이름과 달리 **주방향 광도(cd)** 입니다.
셰이더가 `Radiance = flux / d²` 로 쓰고 `getPower() = 4π·flux` 로 계산합니다.

| 종류 | 변환 |
|---|---|
| 점광원 | `I = Φ / 4π` |
| IES 스포트 | `I = Φ × (축상 광도 / 적분 광속)` — **배광을 그대로 보존** |
| 원뿔만 아는 스포트 | `I = Φ / Ω`, `Ω = 2π(1−cos θ)·(1−0.5·softness)` |
| 면광원 | `I = L × A`, 반각 88° 원뿔로 근사 |

세 번째 식은 RTXPT 자신의 `getShapingFluxFactor` 와 같은 근사입니다. 그래야 광원
선택 가중치와 실제 밝기가 어긋나지 않습니다.

**IES 는 근사하지 않습니다.** 배광을 아는데 균일 원뿔로 뭉개면
이 모델에서 **2.37배 어두워집니다**.

## 4. 세 개의 함정 (전부 조용히 틀리는 종류입니다)

### 4.1 `outerAngle` 은 반각입니다

Donut 헤더의 주석은 이렇게 말합니다.

> `float outerAngle = 180.f;` — *Apex angle of the light cone, in degrees*

**RTXPT 는 그렇게 쓰지 않습니다.**

```cpp
// LightsBaker.cpp
polymorphicEx.CosConeAngleAndSoftness = fp32ToFp16(cosf(dm::radians(abs(spot.outerAngle))));
// LightShaping.hlsli
float coneHalfAngle = acos(shaping.cosConeAngle);
```

`cos(outerAngle)` 을 축과의 내적에 직접 비교하므로 **축에서 잰 반각**입니다.
주석대로 전각을 넣으면 원뿔이 두 배로 벌어집니다.

### 4.2 프록시의 정면은 로컬 **+Z** — Donut 과 정반대입니다

Donut 은 glTF 규약대로 로컬 **−Z** 를 정면으로 봅니다.

```cpp
// SceneTypes.cpp
dm::double3 Light::GetDirection() const {
    return -normalize(double3(localToWorld.m_linear.row2));   // 로컬 -Z
}
```

**Enscape 는 +Z 입니다.** 문서에 없으므로 실측했습니다
(`tools/sketchup/iris_lights_axis.rb`).

| 정의 | 로컬 +Z 의 월드 방향 | 아래를 향한 인스턴스 |
|---|---|---|
| `Enscape.SpotLight#2` | (0, 0, −1) | 3 / 3 |
| `Enscape.SpotLight#1` | (0, +0.26, −0.97) | 8 / 8 |
| `Enscape.SpotLight#3` | (0, 0, −1) | 4 / 4 |
| `Enscape.SpotLight#4` | (0, 0, −1) | 28 / 28 |

**43개 전부**입니다. 15° 기울어진 월워셔(`#1`)까지 같은 규약을 따릅니다 —
우연이 아닙니다.

그대로 두었다면 **다운라이트 43개가 전부 천장을 비췄을 것**입니다. 화면은
어두워지지만 오류는 나지 않으므로, 실측하지 않았다면 "조명이 약하다"고
잘못 진단했을 겁니다.

고치는 방법: 광원 잎을 인스턴스 노드에 직접 달지 않고 **X축 180° 회전한 자식
노드**에 답니다. 자식의 −Z 가 부모의 +Z 가 됩니다. 인스턴스 노드의 변환은
건드리지 않습니다 — 그것은 호스트가 보낸 값이고 델타 추적이 그 위에서 돕니다.

> 사각 광원은 애매합니다. 로컬 +Z 가 월드 +Y(수평)를 향합니다. 높이 1.64 m 에
> 4개가 나란히 있으므로 **벽면 패널**로 보는 것이 자연스럽고, 그렇다면 +Z 규약이
> 일관되게 맞습니다. 다만 "그 그룹이 90° 돌아가 있고 실은 아래를 향한다"는
> 해석도 이 데이터만으로는 배제할 수 없습니다. 스포트라이트의 증거를 근거로
> **모든 종류에 +Z 규약**을 적용하고, 화면에서 어색하면 다시 봅니다.

### 4.3 반지름 0인 스포트라이트는 검증되지 않았습니다

```cpp
if (spot.radius == 0.f)
{
    assert(false); // not tested with radius == 0
```

0 이면 `kPoint` 경로로 빠지고 **원뿔 성형이 적용되지 않습니다** — 스포트라이트가
전방위 점광원이 됩니다. 반드시 양수를 줍니다(기본 25 mm).

## 5. 재질 — 같은 발상, 더 큰 효과

### 5.1 스키마 — `Enscape.Material` / `MaterialData`

```xml
<SketchupMaterial Version="5">
  <TypeV5>GENERIC</TypeV5>          <Opacity>1</Opacity>
  <Roughness>0.83</Roughness>       <Metallic>0.109</Metallic>
  <Specular>0.19</Specular>         <IndexOfRefraction>0</IndexOfRefraction>
  <EmissiveColor>#FFFFFF</EmissiveColor>  <EmissiveStrength>5076.7</EmissiveStrength>
  <BumpAmount>2.9999</BumpAmount>   <BumpMapType>BUMP</BumpMapType>
  <NormalMapIntensity>0</NormalMapIntensity>  <IsSolidGlass>false</IsSolidGlass>
  <DiffuseTexture>…</DiffuseTexture>  <BumpTexture>…</BumpTexture>
</SketchupMaterial>
```

**135개 중 26개**에 값이 있습니다. `_sofa fabric` 은 거칠기 0.83 · 금속성 0.109 ·
Specular 0.19 · 범프 3.0 — 설계자가 직접 정한 값입니다.

이것이 *"재질이 섬세하지 않아요"* 에 대한 답입니다. 추측한
`roughness 0.5 / metalness 0` 고정을 **실제 값**으로 바꿉니다.

### 5.2 미결정 B 의 일부가 답을 얻었습니다

[08번 7.4절](08-재질상속.md)에서 세 가지 접근을 두고 미뤄 뒀습니다. 세 번째 —
**Enscape 재질 속성 읽기** — 가 답입니다. 다만 Enscape 모델에만 해당하므로
나머지 109개와, Enscape 를 쓰지 않은 모델은 여전히 미결정 B 입니다.

`Specular` 는 Donut 의 금속-거칠기 모델에 대응 필드가 없어 지금은 **세기만
집계**합니다. 반영 방식은 미결정 B 에서 정합니다.

### 5.3 자체발광 — 천장 조명의 정체

`SELF_ILLUMINATED` 재질 3종의 `EmissiveStrength` 는 3472 · 5077 · 7000 입니다.
**천장 조명 기구 29개는 Enscape 광원이 아니라 이 재질로 빛납니다.**

반영하지 않으면 실내가 어둡습니다. RTXPT 의 `LightsBaker` 는 발광 삼각형을
광원으로 처리하므로 재질에 값만 넣으면 됩니다.

> [08번 6절](08-재질상속.md)에 적어 둔 제약이 여기서 걸립니다 — `LightsBaker` 는
> `geometry->material` 을 봅니다. **인스턴스 덮어쓰기로 넣은 발광은 광원으로
> 잡히지 않습니다.** 이 모델의 발광 재질은 면에 직접 칠해져 있어 문제없습니다.

## 6. 측광 단위와 렌더러 라디언스

Enscape 값은 물리 단위(cd, cd/m²)이고 **렌더러는 그렇지 않습니다.** 환경맵의
하늘이 대략 1.0 인 스케일로 돌아갑니다. 그대로 넣으면 5000배 밝아집니다.

그래서 한 개의 변환 상수를 둡니다 — **1.0 = 5000 cd/m²** (흐린 하늘의 휘도).

| 확인 | |
|---|---|
| 천장 패널 5077 cd/m² | → **1.02** — 하늘과 비슷한 밝기. 맞습니다 |
| 점광원 989 lm, 2 m 거리 | → 벽면 5 cd/m² = 0.001. 실내 조명은 주광보다 훨씬 어둡습니다 |
| IES 스포트, 3 m 거리 | → 2783 cd/m² = 0.56. 밝은 연출 조명 |

절대 밝기는 노출이 흡수합니다. **이 한 값이 지키는 것은 조명끼리·발광
재질끼리의 상대 비율**이고, 그것이 그림의 인상을 정합니다.

`SceneBuilder::SetPhotometricScale` 로 바꿀 수 있습니다. 정식화는 미결정 B.

### 7.0 배선 확인 (2026-09-08)

여섯 단계를 지나가는 동안 어느 한 곳이 필드를 흘리면 **오류 없이 조용히** 조명이
사라집니다. 실제로 `strip_def` 가 떨어뜨릴 뻔했습니다(`d.dup` 이라 살았습니다).

실제 모델 종단 확인:

```
읽기 OK 28.2 ms — 정의 707 · 머티리얼 99 · 뷰 5
구축 OK 497.1 ms — 메시 422 · 지오메트리 546 · 인스턴스 1331 · 삼각형 399916
조명 — 점 18 · 스포트 48 · 총 광속 2,156,588 lm · 발광 재질 6 · Specular 지정 5
```

프로브가 센 **직접 배치 52개**와 렌더러의 **66개**가 다른 것은 정상입니다 —
광원을 담은 그룹 자체가 여러 번 배치되므로 씬 그래프에서 전개됩니다.
지오메트리도 줄었습니다(메시 426→422 · 인스턴스 1360→1331): 프록시가 빠진 것입니다.

합성 씬으로는 **방어 경로**를 고정했습니다. 조명 정의 7개 중 4개만 살아남아야 합니다:

| 정의 | 기대 |
|---|---|
| spot · point · rect | 통과 |
| `badcone` (원뿔 150°) | 반각 범위로 조여서 **살림** |
| `bogus` (종류 불명) | 버림 |
| `negative` (세기 음수) | 버림 |

> 이 시험을 넣다가 **시험 자체의 버그**를 찾았습니다. 오류 경로 시험이
> `good.begin() + 65536` 으로 잘라 왔는데, 36 MB 모델만 쓰는 동안에는 문제가
> 없다가 6 KB 짜리 합성 씬에서 끝을 넘어가 세그폴트로 죽었습니다.
> **시험이 입력 크기를 가정하고 있었습니다.**

### 7.1 프록시 지오메트리는 렌더하지 않습니다

프록시는 광원 자리를 표시하는 컴포넌트입니다. Enscape 도 그리지 않습니다.
그리면 조명 앞에 작은 물체가 떠서 빛을 가립니다.

**프로브 단계에서 뺍니다** — 정의를 만나는 즉시 광원인지 보고, 맞으면 면 추출을
건너뜁니다. 전송량도 줄고 렌더러가 판단할 일도 없습니다.

RTXPT 에는 `LightExtension::Proxies` 로 발광 기구를 광원과 연결해 **이중 계상을
막는** 장치가 따로 있습니다. 우리 프록시는 발광이 아니므로 지금은 쓰지 않지만,
5.3의 발광 기구를 광원과 짝지을 때 쓸 자리입니다.

### 7.2 면광원은 근사입니다

`Rect`·`Linear` 는 발광 지오메트리로 내지 않고 **반각 88° 원뿔 + 등가 면적의
구면 광원**으로 근사합니다. 반각 88°의 실효 입체각이 거의 정확히 π 라서
램버시안 패널의 축상 광도와 맞습니다.

정확한 면광원은 발광 쿼드를 만들어야 하며, 52개 중 5개이므로 뒤로 미룹니다.

## 8-b. 태양 (2026-09-08)

SketchUp 은 인공 광원은 주지 않지만 **태양은 줍니다.** `model.shadow_info` 에
날짜·시각·위치가 들어 있고 그것이 방향을 정합니다.

### 엔진에 없던 것

셰이더에는 `kDirectional` 이 **이미 구현돼 있었습니다**
(`PolymorphicLight.hlsli` 의 `DirectionalLight::Create`). CPU 쪽 `ConvertLight`
에만 빠져 있었습니다 — RTXPT 는 태양을 환경맵에 구워 오는 것을 전제하기
때문입니다. 건축에서는 그럴 수 없습니다. 환경맵에 구우면 **시각을 바꿀 수
없습니다.**

`DirectionalLightEx` 를 만들었습니다. `LightExtension` 을 함께 상속하는 이유는
`LightsBaker` 가 광원마다 `LightLink`(과거 프레임 대응)를 요구하기 때문입니다.

### 부호 — 실측으로 확정했습니다

`SunDirection` 이 "태양을 향하는" 방향인지 "빛이 나아가는" 방향인지는 문서가
분명하지 않고, 틀리면 **모든 그림자가 정반대로** 집니다.

위경도와 시각으로 태양 고도를 따로 계산해 대조했습니다.

| | |
|---|---|
| SketchUp `SunDirection.z` | −0.363 → 고도 **−21.3°** |
| 위경도·시각으로 계산한 고도 | **−20.0°** |

일치합니다 — **`SunDirection` 은 태양을 향하는 방향**입니다. Donut 은 노드의
로컬 −Z 를 빛의 진행 방향으로 보므로, 노드의 **+Z 를 태양 쪽**에 둡니다.

> 방위는 북 기준으로 거울상이었습니다(SketchUp 27.9° vs 계산 329.2°).
> 그것은 SketchUp 이 **자기 그림자를 그릴 때 쓰는 값**이므로 우리가 맞출
> 대상이지 고칠 대상이 아닙니다.

### 하늘이 태양을 소유합니다 — 이중 그림자

실외 모델에서 **그림자가 두 개**로 나왔습니다. HDRI 환경맵에 태양이 구워져
있는데 거기에 우리 방향광을 더했기 때문입니다. 실내에서는 하늘이 거의 안
보여 드러나지 않았습니다.

RTXPT 에는 절차적 하늘(`SampleProceduralSky`, Q2RTX 대기 산란 모델)이 이미
있고 상수에 `SunDir` 이 있습니다. 다만 **시각 스칼라로만** 계산하고 실제 태양
벡터를 받지 않아서, 호스트 방향을 주입할 수 있게 고쳤습니다(패치 0014).

태양이 있으면 절차적 하늘 + 하늘의 태양 하나. 없으면(실내·그림자 꺼짐·밤)
기존 HDRI 를 그대로 씁니다.

### 부호와 좌표계를 **다섯 군데** 맞춰야 했습니다

전부 "방향"이라는 같은 단어를 쓰면서 뜻이 다릅니다.

| 곳 | 규약 | 틀리면 |
|---|---|---|
| SketchUp `SunDirection` | **태양을 향하는** 방향 (Z-up) | 그림자가 정반대 |
| Donut `Light::GetDirection` | 노드 로컬 **−Z** (glTF 규약) | 그림자가 정반대 |
| 엔진 씬 | **Y-up** | — |
| 대기 산란 (`GetSkyRadiance`) | **Z-up** (`camera = (0,0,6360.1)`) | 밤이 됨 |
| `EnvMapBaker` → 하늘 | **Y·Z 맞바꿈** (아래) | **방위만** 어긋남 |

마지막 것이 가장 오래 걸렸습니다. `EnvMapBaker.hlsl` 이 큐브 방향을 하늘에
넘길 때 이렇게 합니다.

```hlsl
float3x3 toLocal = { 1,0,0,  0,0,1,  0,1,0 };   // Y 와 Z 를 맞바꿈
float3 localDirection = mul( cubeDir, toLocal );
```

**`SunDir` 도 같은 변환을 거친 값이어야 합니다.** 그러지 않아 방위가 어긋났습니다.

#### "고도는 맞고 방위만 틀렸다" 가 단서였습니다

맞바꾸기는 **위 성분을 보존합니다.** 그래서 잘못된 벡터를 넣어도 고도는
맞게 나오고 방위만 어긋납니다. 이 비대칭이 원인을 좁혀 주었습니다.

가는 길에 두 번 빗나갔습니다.

| 넣은 것 | 결과 | 오해 |
|---|---|---|
| 월드 Y-up 벡터 | 밤 | "부호가 반대구나" |
| 뒤집은 것 | 수평선 노을 | "여전히 반대구나" |
| Z-up 벡터 | 고도 25.3° 맞음, 방위 틀림 | "좌표계를 맞췄다" |

세 번째에서 **고도가 맞았기 때문에 맞췄다고 착각**했습니다.

### 눈으로 비교하는 것을 그만두고 나서 풀렸습니다

두 화면을 나란히 놓고 "그림자가 오른쪽이냐"를 여러 번 물었지만, 카메라가
조금만 달라도 답이 달라져 **좌표계 문제인지 카메라 문제인지 가릴 수
없었습니다.** 제가 "일치한다"고 잘못 말한 적도 있습니다.

`tools/sketchup/iris_shadow_clock.rb` 를 만들어 **현재 카메라와 태양으로
기대되는 시계 방향을 계산**하자 한 번에 정해졌습니다.

```
기대  2.7시
SketchUp  2시30분   <- 일치
IRIS      1시30분   <- 틀림
```

> 화면 비교는 관측자(사람)와 관측 대상(카메라)이 함께 움직여서 기준이 없습니다.
> **기준을 계산으로 만들면** 두 화면 중 어느 쪽이 틀렸는지 즉시 갈립니다.

### 확인 (2026-09-08)

| | |
|---|---|
| 고도 | 하늘 기본 71.0°(midday) · 우리 25.3° = SketchUp 값 |
| 방위 | 계산 2.7시 = SketchUp = **IRIS** (수정 후 사용자 확인) |
| 그림자 개수 | **1개** |

> SketchUp 뷰포트에서 그림자가 안 보이던 것은 밝음 슬라이더가 아니라
> **바닥 면이 가리고 있었기** 때문이었습니다. 바닥을 지우자 바로 보였습니다 —
> 제가 밝음을 의심한 것은 틀렸습니다.

### 넣지 않는 두 경우

| | 왜 |
|---|---|
| 호스트에서 그림자가 꺼져 있음 | 설계자가 일부러 끈 것을 렌더러가 되살리면 화면이 호스트와 달라집니다 |
| 태양이 지평선 아래 | 그대로 넣으면 **땅 밑에서 빛이 올라옵니다** |

둘 다 조용히 넘어가지 않고 이유를 남깁니다.

### 실측 모델에서 걸린 것

외부 모델(포르쉐 성수 전체, 삼각형 131만)에서 셋이 겹쳐 있었습니다.

```
DisplayShadows = false           그림자가 꺼져 있음
City           = "Boulder (CO)"  SketchUp **기본 위치**. 성수동이 아님
ShadowTime     = 22:56           고도 -21.3도 = 밤
```

**위치가 기본값으로 남아 있는 것이 특히 중요합니다.** 한국 프로젝트인데 태양이
미국 콜로라도 기준으로 계산됩니다. 이것은 IRIS 의 결함이 아니라 모델의 설정
문제이지만, **렌더러가 말해 주지 않으면 아무도 모릅니다.** 리포트에 도시와
위경도를 함께 찍습니다.

## 8-g. IES 배광 — 켰습니다 (2026-09-11)

3.3절이 "셰이더의 `evaluateIesProfile` 이 비어 있다"고 적어 둔 항목입니다.

### 먼저 얼마나 좋아지는지 쟀습니다

원뿔 근사를 RTXPT 의 **실제 감쇠식**과 견줬습니다 — 각도가 아니라
`smoothstep(cos(outer), cos(outer) + softness, cos(theta))` 이고
`softness = 1 - inner/outer` 는 **코사인에 더하는 수**입니다(LightsBaker.cpp).

Bega 8331 WIDE (골프존, 세로 19 x 가로 19, 최대 5,969 cd):

| | |
|---|---|
| 유도한 원뿔 | 안쪽 29.8도 · 바깥 54.3도 |
| **세로 최대오차** | **0.190** (30도에서) · RMS 0.085 |
| **가로 비대칭** | **0.809** |

세로 19% 도 크지만 가로가 결정적입니다. 월워셔라 세로 30도에서 방위에 따라
0.209 ~ 0.495 인데 우리는 **가로 전체의 최댓값**을 써서 좁은 쪽을 2.4배
밝게 칠했습니다. 1차원으로는 담을 수 없습니다.

### 리샘플러는 오프라인에서 먼저 검증했습니다

`attrs_dump.txt` 에 남아 있던 실제 base64 로 파이썬 프로토타입을 돌려
원래 격자점을 되짚었고 **최대오차 0.000000** 이었습니다. 그다음 Ruby 로
옮겼습니다([[reproduce-before-blaming-renderer]] 와 같은 방식).

⚠ **폭이 세로각, 높이가 가로각**입니다. 셰이더가
`u = acos(dot(dir,axis))/pi`, `v = atan2(y,x)/(2pi)+0.5` 로 읽습니다.
뒤집으면 배광이 90도 돌아간 채 그럴듯하게 나옵니다.

IES 대칭 규칙(0..90 사분 · 0..180 좌우 · 0..360 전체)으로 접고, 파일이 안
다루는 세로각은 0 입니다.

### `#if 0` 은 "구현이 없어서"가 아니었습니다

켜 보니 **컴파일이 안 됐습니다.** 네 가지가 없습니다.

| 없는 것 | 어디에 |
|---|---|
| `c_pi` | 아예 없는 이름 (`K_PI`) |
| `t_BindlessTextures` | RTXDI · LightsBaker |
| `s_MaterialSampler` | 같음 |
| `BranchlessONB` | LightsBaker |

`LightShaping.hlsli` 는 **세 군데**에서 포함되고 각각 가진 것이 다릅니다.
게다가 경로 추적기에서도 이 헤더가 **바인딩보다 먼저** 파싱됩니다 —
`PathTracerBridgeDonut` 17행이 `PathTracerBridge` 를 포함하고 그게 여기까지
끌고 오는데 바인딩은 29~31행입니다. 매크로를 뒤에서 켜면 "이미 정의됨"
오류만 납니다(실제로 겪었습니다).

그래서 **텍스처 한 번 읽기만** 전방 선언으로 갈랐습니다.

```hlsl
// LightShaping.hlsli — 선언만 (바인딩 없는 곳에서는 1.0 정의)
float IrisSampleIesProfile(int profileIndex, float2 uv);

// PathTracerBridgeDonut.hlsli — 바인딩이 다 들어온 자리
float IrisSampleIesProfile(int profileIndex, float2 uv)
{
    Texture2D<float4> tex = t_BindlessTextures[NonUniformResourceIndex(profileIndex)];
    return tex.SampleLevel(s_MaterialSampler, uv, 0).x;
}
```

각도 계산과 정규직교기저는 의존성 없이 그 자리에서 끝냅니다.

### 원뿔을 넓혀야 합니다

셰이더는 `softSpotlight * iesMultiplier` 로 **곱합니다**. 배광에서 유도한
원뿔(바깥 54.3도)을 그대로 두면 그 바깥의 배광이 잘려 나갑니다 — Bega 8331
은 55~80도에도 빛이 있습니다(0.094 ~ 0.002). 배광을 붙일 때 원뿔을 89도로
넓히고, 모양은 배광이 정하게 합니다. 원뿔은 광원 선택의 경계로만 남습니다.

### 실측

골프존 · 3840x2036 · 같은 카메라:

| | IES 끔 | IES 켬 |
|---|---|---|
| 광원 | 62 | 62 |
| FPS | 45.2 | 44.4 |
| 배광 | — | 1종을 광원 43개가 씀 (128 x 64 텍스처) |

성능은 같고, 화면은 예상한 방향으로 바뀝니다 — 빛이 기구 가까이로 모이고
중간 각이 어두워집니다(원뿔 근사는 30도에서 0.685, 실제는 0.495).

끄려면 IRIS 패널의 `IES photometric profiles` 를 끕니다 (8-h). 시험용으로
한 번만 끄려면 환경변수 `IRIS_IES=0`.

### 방향 검증 — **맞출 수 없습니다** (2026-09-11)

화면을 더 보는 대신 코드를 읽어 답을 얻었습니다.

```hlsl
// LightShaping.hlsli
BranchlessONB(lightPrimaryAxis, xAxis, yAxis);   // 축 하나로만 기저를 만듭니다
```

```cpp
// PolymorphicLight.h
struct PolymorphicLightInfoEx {
    uint IesProfileIndex;
    uint PrimaryAxis;                // 방향뿐 — 접선이 없습니다
    uint CosConeAngleAndSoftness;
    uint UniqueID;                   // 디버그용
};
```

가로각의 기준이 **광원의 방향 벡터 하나**에서 만들어집니다. 기구가 자기 축을
중심으로 얼마나 돌아가 있는지는 어디에도 전달되지 않습니다. 축대칭 배광이면
상관없지만, 비대칭 배광(Bega 8331 WIDE 는 0.809)은 **임의 각도로 돌아간 채**
그려집니다. 그럴듯하고 눈으로는 못 잡습니다.

2차원을 보내는 것은 **틀린 것을 정밀하게 그리는 일**입니다.

### 그래서 방위 평균으로 접습니다

방향을 모를 때 에너지가 맞는 값은 방위 평균입니다. 실측:

| 세로각 | 원뿔 | 지금까지(가로 최댓값) | 방위 평균 |
|---|---|---|---|
| 25도 | 0.803 | 0.639 | **0.453** |
| 30도 | 0.685 | 0.495 | **0.340** |

| | 최대오차 |
|---|---|
| 원뿔 vs 평균 | **0.350** |
| 가로 최댓값 vs 평균 | **0.186** |

**얻는 것** — 세로 배광이 정확해집니다. 원뿔이 25~30도에서 0.35 만큼 과다
조명하던 것이 사라집니다. 축 위(0도)는 평균 = 최댓값이라 축상 광도가
정확히 보존됩니다.

**포기하는 것** — 좌우 비대칭. 다만 **전에도 표현하지 못했고**, 가로
최댓값을 써서 0.186 만큼 과다했습니다. 평균이 그보다 낫습니다.

텍스처는 `IES_NV x 1` 이 됩니다.

### 제대로 고쳤습니다 — 기구의 회전을 보냅니다

`PolymorphicLightInfoEx` 는 네 칸이 다 차 있습니다. 하지만 **다른 데
자리가 있었습니다** — 구면 광원(스포트가 변환되는 형태)은
`Base.Scalars` 의 **하위 16비트(radius)만** 씁니다.

```cpp
// LightsBaker.cpp — 스포트, radius > 0
polymorphic.Scalars = fp32ToFp16(spot.radius);          // 하위 16비트
polymorphic.Scalars |= (uint32_t)fp32ToFp16(roll) << 16; // IRIS: 상위에 롤
```

롤은 **노드 변환의 row0(기구의 로컬 +X)** 가 ONB 기저에서 몇 도에 있는지
입니다.

```cpp
const float3 t = tangent - axis * dot(tangent, axis);
roll = std::atan2(dot(t, yAxis), dot(t, xAxis));
```

```hlsl
// 셰이더 — 그만큼 빼고 감쌉니다
const float tangentAngle = atan2(emissionDirection.y, emissionDirection.x) - iesRoll;
const float normTangentAngle = frac(tangentAngle * .5f / K_PI + .5f);
```

⚠ **ONB 식을 CPU 와 셰이더에 똑같이 써야 합니다.** 한쪽만 고치면 롤이
어긋난 채 그럴듯하게 나옵니다. 양쪽 주석이 서로를 가리킵니다.

방향이 정해지므로 호스트를 **2차원으로 되돌렸습니다**(`IES_NH` 1 -> 64).
비대칭 0.809 가 제자리에 그려집니다.

**남은 전제 하나** — Enscape 프록시의 로컬 +X 가 IES 가로각 0도라고 봤습니다.
90도 어긋나 있다면 모든 비대칭 배광이 **같이** 90도 돌아가므로 상수 하나로
교정됩니다. 인스턴스마다 제각각이던 상태와는 다릅니다.

🔴 **그 전제가 틀렸습니다.** 실제로 90도 어긋나 있었고, 아래 「통제 시험」
에서 잡아 `row0` -> `row1` 로 고쳤습니다. 예상대로 상수 하나였습니다.

실측(골프존 · 3840x2036): `Bega.8331WIDE.IES@128x64` 를 광원 43개가 씁니다.

### 곁가지 — 조용히 낡은 텍스처

배광 캐시의 키가 **파일명뿐**이었습니다. 격자를 128x64 에서 128x1 로 바꿨는데
키가 같아서 엔진의 프로세스 수명 캐시가 **옛 텍스처를 그대로 내줬습니다.**
화면도 로그(`1종을 광원 43개가 씁니다`)도 정상이었고, 새 "구움" 줄이
없는 것을 보고서야 알았습니다. 키에 크기를 넣었습니다.

### 0도 방위 검증 — 배치가 답을 줍니다 (2026-09-11)

#### 먼저 막힌 길 셋

**① Enscape 는 회전을 저장하지 않습니다.** IES 조명의 `LightData` 전체가
이것뿐입니다 (광원 정의 5종에서 확인):


인스턴스 사전에도 없습니다(`SU_InstanceSet` 의 `Owner`/`Status` 뿐).
**방위 기준은 오로지 프록시 변환에서 나옵니다** — 우리와 같은 처지입니다.

**② IES 헤더도 못 가립니다.** LM-63 은 광원 개구부의 **폭을 90-270축,
길이를 0-180축** 방향으로 적게 합니다. 기구가 길쭉하면 헤더가 0도 평면을
알려 주는 셈입니다. 그런데:

```

TILT=NONE
 1  8500  8.5  19  19  1  1  1.1  1.1  0
                              ^^^  ^^^  폭 = 길이 = 1.1 ft (정사각)
```

프록시 지오메트리도 정사각입니다(X = Y, 네 정의 모두). 제조사 머리말에도
방향 언급이 없습니다.

**③ 그러나 틀릴 수 있는 각도는 하나뿐입니다.** 가로각이 0~90 — **사분
대칭**입니다. 180도 회전은 자기 자신이라 티가 안 납니다. 남은 가능성은
**90도냐 아니냐, 둘뿐**입니다. 그리고 배광은 실제로 길쭉합니다:

| 방위 평면 | 반치각 |
|---|---|
| 0도 (우리 기준으로 로컬 +X) | **18.0도** |
| 90도 (로컬 +Y) | **29.8도** |

90도 틀리면 넓은 축과 좁은 축이 통째로 뒤바뀝니다.

#### 답을 준 것 — 한 줄로 늘어선 여덟 개

`Enscape.SpotLight#1` 의 배치 8개:

```
배치선   (0.998 -0.058 0.000)   퍼짐 537.7 인치 (직교 방향 18.2)
방출 축  (0.000  0.259 -0.966)   — 15도 기울어 있습니다
기운 쪽  (0.000  1.000  0.000)   · 배치선과 |cos| 0.058  (직교)
```

한 줄로 13.7 m 늘어서 있고(직교 방향 퍼짐은 18 인치뿐 — 곧은 선), 줄과
직각으로 15도 기울어 있습니다.

⚠ **처음에 이걸 「월워셔」라고 단정했다가 틀렸습니다.** 광선을 쏴 보니
빔은 벽이 아니라 **바닥**에 떨어집니다 — `(1521, 951, 0)`, 기구 바로 앞
23 인치입니다. 1.7 m 떨어진 벽에 닿으려면 15도로는 어림없습니다.
이름을 붙이기 전에 광선부터 쏴야 했습니다.

남는 것은 약해진 형태의 같은 논리입니다. **한 줄로 늘어선 기구는 넓은
축이 줄을 따라가야** 사이가 고르게 덮입니다. 1.95 m 간격인데 좁은 축을
줄 방향으로 두면 사이가 빕니다.

```
좁은 축 로컬 +X (0.000 -0.966 -0.259) · 배치선과 |cos| 0.056   (직교)
넓은 축 로컬 +Y (-1.000 0.000  0.000) · 배치선과 |cos| 0.998   (나란)
```

`#2`(3개)·`#3`(4개)도 곧은 줄이고 같은 결과입니다. `#4`(28개)는 줄이 아니라
격자라 단서가 없습니다.

여기서 "저작자는 Enscape 화면을 보며 배치했을 테니 우리 기준으로 읽어
맞는 설계가 나오면 두 규약이 같다"고 결론지었습니다.

#### 🔴 그 결론은 **틀렸습니다** (2026-09-11, 통제 시험)

아래 「통제 시험」 절이 답입니다. **Enscape 의 0도 방위는 로컬 +Y** 이고,
우리는 90도 어긋나 있었습니다.

추론이 왜 빗나갔는지는 분명합니다 — 이 배치가 **어느 쪽으로 읽어도
말이 되기** 때문입니다. 좁은 축을 줄 방향으로 두는 것도(빛이 서로 안 겹치게)
설계로 설명됩니다. 설계 의도는 **한 방향으로만 읽히지 않으면 증거가 못
됩니다.** 그럴듯함을 근거로 삼은 것이 잘못이었습니다.

#### 렌더로 못 박으려 했고 — **가려지지 않았습니다** (2026-09-11)

같은 뷰를 Enscape 와 IRIS 로 렌더해 견줬습니다. IRIS 쪽에 상수 오프셋
스위치를 넣어 0도와 90도 두 변종을 만들었습니다:

```

```

결과: **골프 베이 실내 뷰에서 0도와 90도가 구별되지 않습니다.** 노출을
고정하고 같은 카메라로 찍어도 두 장이 사실상 같습니다.

⚠ 처음에는 자동 노출로 찍고 "0도가 Enscape 와 더 닮았다"고 읽었는데,
**그 차이는 톤매퍼가 만든 것**이었습니다. 노출을 고정하니 사라졌습니다.
자동 노출은 전역 밝기 차이를 상쇄하므로 A/B 에는 쓰면 안 됩니다 —
8-h 의 흐림 검증에서 배운 것과 같은 함정입니다.

IES 는 두 실행 모두 활성이었습니다(`IES 배광 — 1종을 광원 43개가 씁니다`).
설정이 아니라 **장면이 가리지 못하는 것**입니다:

- 배광의 길쭉함이 1.65 : 1 (반치각 29.8도 대 18.0도) 로 완만합니다
- 광원 43개의 웅덩이가 서로 겹칩니다
- 빔이 닿는 바닥이 짙은 색 인조잔디라 무늬가 안 읽힙니다

실제 장면이 가리지 못한 것이지 배관 문제가 아닙니다. 다음 절에서 장면을
단순하게 만들어 답을 얻었습니다.

복잡한 장면이 가리지 못했던 이유를 전부 없앱니다 — 광원 하나, 흰 바닥,

#### 결과

| | 바닥 웅덩이 |
|---|---|
| **Enscape** | **가로로 길쭉** (월드 X, 약 1.64 : 1) |
| IRIS — 로컬 +X 를 0도로 (그때까지의 우리 기준) | **세로로 길쭉** (월드 Y) |

1.64 : 1 은 배광 자체의 29.8도 : 18.0도 와 맞습니다. 눈으로 바로 갈립니다.

**Enscape 의 IES 가로각 0도 평면은 프록시의 로컬 +Y 입니다.** 우리는 +X 로
보고 있었고, 그래서 비대칭 배광 전부가 90도 돌아간 채 그려졌습니다 —
넓은 축과 좁은 축이 통째로 뒤바뀐 채로.

#### 고침

```cpp
// LightsBaker.cpp
float3 tangent = float3(0.0f, 1.0f, 0.0f);
if (auto node = spot.GetNode())
    tangent = -float3(node->GetLocalToWorldTransform().m_linear.row1);
```

`row0`(로컬 +X) 이 아니라 `row1`(로컬 +Y) 입니다. 부호를 되돌리는 이유는
광원 잎이 **X축 180도 회전한 자식 노드**에 달려 있기 때문입니다
(SceneBuilder.cpp — 프록시 정면이 로컬 +Z 라서). 그 회전이 Y 를 뒤집습니다.
사분·좌우 대칭 배광에서는 부호가 무의미하지만, 가로각 0~360 짜리 완전
비대칭 배광에서는 180도 어긋납니다.

고친 뒤 같은 시험에서 오프셋 없이 Enscape 와 같은 가로 웅덩이가 나옵니다.

#### 배운 것

**설계 의도는 한 방향으로만 읽히지 않으면 증거가 못 됩니다.**

배치 분석은 "한 줄로 늘어선 기구는 넓은 축이 줄을 따라가야 고르게
덮인다"였습니다. 그런데 **좁은 축을 줄 방향으로 두는 것도** 설계로
설명됩니다 — 기구끼리 빛이 겹치지 않게. 어느 쪽으로 읽어도 말이 되는
근거로 결론을 냈고, 틀렸습니다.

그리고 **자동 노출로는 A/B 를 하면 안 됩니다.** 이 절에서만 두 번
걸렸습니다 (흐림 검증 8-h 에서 한 번 더). 톤매퍼가 전역 차이를 상쇄해
"닮았다/다르다"를 만들어 냅니다.

## 8-f. 면광원 — 발광 지오메트리로 (2026-09-11)

### 근사가 생각보다 정확했습니다

사각·선형 광원을 88도 원뿔 + 등가 면적 구면으로 냈습니다. 7.2절은 이것을
"근사"라고만 적었는데, 엔진을 읽어 보니 꽤 정확합니다:

```cpp
// LightsBaker.cpp — 반지름이 0 이 아닌 스포트
float projectedArea = PI * (spot.radius * spot.radius);
float3 radiance     = spot.color * spot.intensity / projectedArea;
... PolymorphicLightType::kSphere ...
```

우리가 `r = sqrt(A/pi)`, `intensity = L * A` 를 주므로 **투영 면적과
라디언스가 정확히 맞고**, kSphere 라서 부드러운 그림자도 나옵니다.

틀리는 것은 셋이었습니다.

| | 구면 근사 | 실제 |
|---|---|---|
| 모양 | 원형 | 사각형 |
| 길쭉함 | 0.02 x 2 m 가 반지름 0.11 m 공 | 2 m 선 |
| 코사인 | 원뿔 안에서 고르게 | 기울면 어두워짐 |

### 발광 삼각형은 한쪽만 빛납니다

```hlsl
// PolymorphicLight.hlsli — TriangleLight::CalcSample
float cosTheta = dot(normal, -dir);
if (cosTheta <= 0.f) return result;
```

패널과 정확히 맞습니다. Enscape 프록시의 정면이 로컬 +Z 이므로 법선을 +Z 로
두면 그대로입니다 — 스포트와 달리 X축 180도 뒤집기가 **필요 없습니다**
(스포트는 Donut 광원이 -Z 를 향하기 때문에 필요했습니다).

### 구현

단위 사각형(XY 평면, 법선 +Z) 하나를 인스턴스마다 `(w, l, 1)` 로 늘립니다.
라디언스·색이 같으면 같은 메시라 BLAS 도 재사용됩니다 — 39종 298개가
메시 39개가 됩니다. 재질은 `emissiveIntensity = radiance * 측광배율` 로,
Enscape 자체발광 재질과 같은 경로입니다(`radiance = lm / (pi * A)`).

### 찍어서 정했습니다

포르쉐 성수 1F 실내, 3840x2036, 같은 카메라:

| | 면광원 OFF | 면광원 ON |
|---|---|---|
| 천장 | **동그란 빛 웅덩이** | **사각 패널 · 긴 라인** |
| FPS | 31.1 | **31.5** |
| 분석 광원 | 777 | 479 |
| 메시 / 인스턴스 | 1286 / 11605 | 1325 / 11903 |

성능은 같고 조명이 건축 조명처럼 보입니다. 걱정했던 것 둘 — 허공에 뜬 흰
사각형, 기구 안에 갇혀 빛이 막히는 것 — 은 **실제로 나타나지 않았습니다.**

**켜는 것이 기본입니다.** 끄려면 IRIS 패널의 `Area lights as emissive
geometry` 를 끕니다 (8-h). 시험용으로 한 번만 끄려면 환경변수
`IRIS_AREA_LIGHTS=0`.

### 통계 한 줄

면광원을 켜면 `총 광속` 이 1억 3,526만 -> 5,226만 lm 으로 떨어집니다 —
빛이 사라진 것이 아니라 분석 광원에서 지오메트리로 옮겨 간 것입니다.
그대로 두면 "씬이 어두워졌다"로 읽히므로 면광원의 광속(`L * pi * A`)을
합계에 같이 넣습니다.

## 8-e. 숨겨진 조명 — 건너뛰는 것이 맞습니다 (2026-09-10)

렌더러는 hidden 노드를 통째로 건너뜁니다(`SceneBuilder.cpp:409`). 조명
프록시가 숨겨져 있으면 그 광원이 아예 안 만들어집니다. 포르쉐 성수 모델에서
`Enscape.RectangularLight#4` 가 배치 43개 전부 숨김으로 나와서, **광원을
잃고 있는 것인지** 확인했습니다.

### 얼마나 손해인가 — 먼저 재고 나서 답합니다

```
조명 배치   885개 중 숨김 62개 (7.0%)
광속        143,859,674 lm 중 숨김 3,697,000 lm (2.570%)
```

문제로 지목했던 `RectangularLight#4` 는 47개 배치에 **총 47,000 lm** —
전체의 **0.03%** 입니다. 화면에 나타날 수 없는 양이었습니다.

### 작성자가 끈 것입니다 — 자료가 그렇게 말합니다

| 정의 | 숨김 | 보임 |
|---|---|---|
| `Enscape.RectangularLight#9` | 3 | 31 |
| `Enscape.RectangularLight#10` | 1 | 27 |
| `Enscape.RectangularLight#26` | 1 | 32 |

**같은 정의인데 일부만 숨겨져 있습니다.** Enscape 가 프록시를 자동으로
숨기는 것이라면 정의 단위로 전부 숨겨야 합니다. 인스턴스마다 다르다는 것은
사람이 하나씩 껐다는 뜻입니다. 그러므로 hidden 을 "끔"으로 읽는 지금
동작이 맞습니다.

이것이 **Enscape 자산**과 갈리는 지점입니다 — 자산(Bush 058, Bush 114)은
`Source=REMOTE` 인 것만, 그리고 **전부** 숨겨져 있었습니다(4/4, 3/3).
그건 Enscape 가 한 것이고, 조명의 섞인 분포는 사람이 한 것입니다.

`tools/sketchup/iris_hidden_lights.rb` 가 근거이고 다시 돌릴 수 있습니다.

## 8-d. 하늘 — 기본값이 흐림이었습니다 (2026-09-10)

실외 모델에서 **그림자가 안 보였습니다.** 태양 방향은 맞고(고도 +27.2도,
방위 278.8도), 자동 노출도 켜져 있고, 화면도 타지 않는데 바닥에 드리우는
그림자가 없었습니다.

원인은 RTXPT 절차적 하늘의 **구름 기본값**이었습니다.

```cpp
SampleProceduralSky.h   float m_cloudDensityOffset = 0.75f;
```

### 이름과 반대로 동작합니다

```hlsl
Density = max(0, Density - cloud_density_offset) / (1.001 - cloud_density_offset);
```

**빼는 문턱값**입니다. 양이 아닙니다.

| 값 | 결과 |
|---|---|
| 0.0 | 노이즈가 그대로 통과 — 하늘 전체에 **옅은 안개** |
| 0.75 (엔진 기본) | 짙은 부분만 남음 — 뚜렷한 구름 |
| **1.0** | 전부 빠짐 — **완전히 맑음** |

이름만 보고 "0으로 내리면 구름이 없어진다"고 읽었다가 틀렸습니다. 0 은
구름을 없애는 것이 아니라 태양을 고르게 흩뜨립니다 — 뚜렷한 구름은 없는데
그림자도 없는, 가장 헷갈리는 상태가 됩니다.

### IRIS 씬은 맑게 시작합니다

건축 프레젠테이션은 대개 맑은 날을 씁니다. 그리고 **SketchUp 그림자 패널에는
날짜·시각·위치만 있고 날씨가 없습니다.** 그러니 이건 호스트가 정할 수 없는
값이고, IRIS 가 정해야 합니다. 8-h 의 설정으로 옮겼습니다.

### 태양 경로는 전부 확인됐습니다

| 단계 | 확인 |
|---|---|
| 호스트 -> 브리지 | `태양 O` (트레이스 로그) |
| 브리지 -> 하늘 | `호스트 로컬 (-0.879 -0.136 0.456) 고도 27.2도` |
| 하늘 -> 환경맵 | 태양 원반이 화면에 보임 (큐브 1024, 원반 0.533도 ~ 6텍셀) |
| 환경맵 -> 그림자 | 바닥에 그림자 생김 |

### `Sun Brightness` 는 답이 아닙니다

```cpp
FinalRadianceMultiplier = brightness * colorTint * m_sunBrightness;
StarIrradiance          = (1.474, 1.850, 1.912) * m_sunBrightness;
```

하늘과 태양을 **같이** 곱합니다. 비율이 안 바뀌므로 이 값을 올려도 그림자는
안 생깁니다. 실제로 후보로 올렸다가 코드를 보고 지웠습니다.

### 무시되는 슬라이더 둘

`Sun time of day offset` 과 `Sun east west rotation` 은 호스트 태양이 있을
때 **아무 효과가 없습니다** — `sunDir = hs` 로 통째로 덮어쓰기 때문입니다.
UI 에 남아 있으므로 값이 0 이 아니어도 놀라지 마십시오. 반대로, 이 슬라이더를
움직여서 그림자가 움직인다면 **주입이 안 되고 있다는 신호**입니다.

## 8-c. Luminosity 의 단위 — 실험으로 확정 (2026-09-10)

### 무엇이 이상했나

포르쉐 성수 모델의 사각 광원이 합계 **8,520만 lm** 입니다. 하나당 평균
299,000 lm — 경기장 투광기 급입니다. 골프존 모델에서는 같은 필드가 2,832
였고 그건 lm 으로 타당했습니다. **같은 필드가 모델에 따라 세 자릿수 다른
값**을 냅니다.

### 자료에 변화가 없으면 상관을 볼 수 없습니다

넓이와의 상관으로 가리려 했습니다. 결과:

| | |
|---|---|
| 사각 광원 정의 | 39종 |
| **Luminosity 가 정확히 같은 것** | **38종** (`300000.00000000012`) |
| 나머지 하나 | `1000` |
| 인스턴스 배율 | 전부 1 — 정의의 W·L 을 믿어도 됨 |
| XML 필드 | `Luminosity` · `Width` · `Length` 뿐. 단위도 배율도 없음 |

**통계가 저를 속일 뻔했습니다.** 38개가 같은 값이라 남은 한 점이 기울기를
혼자 정했고 `기울기 +1.096 · R² 0.386` 이 나왔습니다. 미리 적어 둔 읽는
법대로면 "넓이에 비례한다 = 지금 방식이 맞다"입니다. 계산은 옳고 결론만
틀립니다. **원표를 보고서야 알았습니다.** 이제 회귀보다 퇴화 검사를 먼저
합니다(`iris_rect_probe.rb`).

### 변화를 만들어서 봤습니다

자료에 변화가 없으면 만들면 됩니다. Enscape UI 에서 밝기를 아는 값으로
바꾸고 저장된 수를 읽었습니다(`iris_light_read.rb`, 덧붙여 기록).

| Enscape UI | 저장된 Luminosity |
|---|---|
| 1000 | `1000` |
| 2000 | `2000` |

**1:1 입니다. 우리가 읽는 방식이 맞습니다.** 단위 문제가 아니었습니다.

### 그러면 300,000 은 무엇인가 — 확정

Enscape UI 를 직접 봤습니다.

```
Luminous Power    300,000 lm     <- 슬라이더가 오른쪽 끝
Width             1.499 m
Length            1.956 m
```

**라벨이 `lm` 이고, 300,000 은 슬라이더의 최댓값입니다.** 값에서 역추론했던
단위가 맞았고, 작성자가 사각 광원 38종을 전부 최대로 밀어 둔 것입니다.
씬이 과다한 것은 자료가 그렇기 때문이지 우리가 잘못 읽어서가 아닙니다.

38종이 같은 값인 것은 **하나를 만들어 복사해 쓴** 결과로 보입니다 — W·L 은
0.36 ~ 4.7 m² 로 제각각인데 Luminosity 만 같습니다.

#### 틀린 가설 하나 — 부동소수 꼬리

`300000.00000000012` 의 꼬리를 보고 "슬라이더로 정한 값의 표식"이라고
짐작했습니다. 손으로 친 값(`1000`, `2000`, `100000`)은 정확히 떨어지고
`30000.000000000011` · `989.281329470043` · `83860.4024510768` 에는 찌꺼기가
있었기 때문입니다.

**틀렸습니다.** 슬라이더를 끝까지 밀어 확인하니 `300000` 이 정확히
떨어졌습니다. 꼬리가 어디서 오는지는 여전히 모릅니다. 결론(단위 = lm,
300,000 = 최댓값)에는 영향이 없으므로 적어만 둡니다.

### 진짜 문제는 노출입니다

작성자는 **Enscape 의 자동 노출** 위에서 작업했습니다. 광원을 최대로 밀어도
자동 노출이 정규화하므로 화면은 멀쩡합니다.

우리는 그렇지 않습니다:

```
ToneMappingPasses.h:41   bool autoExposure = false;
```

기본값이 꺼짐이고 **IRIS 는 이 값을 건드리지 않습니다.** 고정 노출로
읽으니 같은 자료가 타 버립니다. 광원 값을 의심할 일이 아니라 노출을
붙일 일이었습니다.

RTXPT 에는 이미 있습니다 — `ToneMappingParameters` 에 `autoExposure` ·
`exposureCompensation` · `exposureValue{,Min,Max}` 가 있고 씬 카메라에서
읽어 옵니다(`Sample.cpp:490`). Enscape 급이 되려면 켜야 합니다. 다만
지금까지의 렌더 비교가 전부 고정 노출 위에서 이뤄졌으므로, 켜는 순간
그 비교 기준이 바뀝니다. 별도로 결정합니다.

### 자동 노출을 켰습니다 (2026-09-10)

```cpp
// Sample.cpp — SceneLoaded()
if (IsIrisScene(m_currentScenePath))
{
    m_ui.ToneMappingParams.autoExposure = true;
    m_ui.ToneMappingParams.exposureCompensation = 0.0f;
}
```

보정을 0 으로 되돌립니다. 엔진이 그 위에서 `exposureCompensation = 2.0f`
를 넣는데, 그것은 예제 씬(어두운 편)에 맞춘 값입니다. 자동 노출이 이미
맞춘 밝기에 다시 **네 배**가 됩니다(`ToneMappingPasses.cpp:432`,
`pow(2, 보정)`).

`IsIrisScene` 은 **파일 이름**으로 견줍니다. `m_currentScenePath` 는
`GetLocalPath(c_AssetsFolder) / sceneName` 이라 앞에 자산 폴더가 붙습니다
(`SetCurrentScene`). 전체 경로를 그대로 견주면 라이브 링크(`IRIS live`)
에서 영영 안 맞고 **조용히 아무 일도 일어나지 않습니다.** 첫 판이 그랬고
빌드는 통과했습니다.

엔진 쪽은 이미 다 있었습니다 — 켜면 휘도 패스가 돌고
(`if(m_AutoExposure)`), `kExposureKey / avgLuminance` 로 곱하고,
`exposureValue{Min,Max}` 가 그 배율의 상하한이 됩니다(-16 ~ +16 스톱).

씬 카메라가 덮어쓰지 않는지도 봤습니다. `UpdateCameraFromScene` 이
`PerspectiveCameraEx` 일 때만 노출을 덮어쓰는데, SceneBuilder 는 평범한
`PerspectiveCamera` 를 만듭니다. SketchUp 뷰를 골라도 자동 노출은 켜진
채로 남습니다.

### 남는 것

- 슬라이더 최댓값 확인 (300,000 인가) — 확정되면 "작성자가 최대로 밀었다"가 증명됩니다
- 노출을 호스트가 정하게 할 것인가 (Enscape 에는 노출 설정이 있습니다)
- `lumen_scale` 은 그대로 둡니다 — 단위가 맞으므로 교정 다이얼이 필요 없습니다

## 8-h. IRIS 설정 — 호스트가 줄 수 없는 것들 (2026-09-11)

SketchUp 그림자 패널에는 **날짜·시각·위치만** 있습니다. 날씨도, 노출도,
조명을 어떻게 변환할지도 없습니다. 그래서 이 값들은 호스트가 정할 수 없고
IRIS 가 가져야 합니다.

그동안은 코드에 박혀 있거나(구름 1.0, 자동 노출 켬) 환경변수였습니다
(`IRIS_AREA_LIGHTS`, `IRIS_IES`). 견주려고 급히 둔 것이라 사용자가 바꿀 수
없고 껐다 켜면 사라졌습니다. 한곳에 모으고 파일에 남깁니다.

```
Rtxpt/Iris/IrisSettings.h        헤더 하나 (CMake 가 GLOB 이라 .cpp 를
                                  늘리면 다시 구성해야 합니다)
%LOCALAPPDATA%\IRIS\settings.json
```

렌더러 설정 창 맨 위 `IRIS` 항목입니다. **호스트 씬일 때만 보입니다** —
엔진 예제 씬에는 뜻이 없는 값들입니다.

| 항목 | 기본 | 언제 먹히나 |
|---|---|---|
| `Cloudiness` | 0 (맑음) | 바로 |
| `Auto exposure` | 켬 | 바로 |
| `Exposure compensation` | 0 EV | 바로 |
| `Area lights as emissive geometry` | 켬 | **다음 sync** |
| `IES photometric profiles` | 켬 | **다음 sync** |

아래 둘은 씬 그래프를 만들 때 정해지므로 지금 화면은 안 바뀝니다. 라벨에
그렇게 적어 뒀습니다.

### 흐림은 엔진 값을 뒤집은 것입니다

8-d 에서 봤듯 엔진의 `cloud_density_offset` 은 **빼는 문턱값**이라 1 이
맑음입니다. 이름만 보고 반대로 읽었던 값입니다. 밖으로는 상식대로 보이게
뒤집고, 그 뒤집힘은 `Settings::CloudDensityOffset()` 한 군데에만 둡니다.

```
흐림 0 -> offset 1.0 (맑음)      흐림 1 -> offset 0.0 (옅은 안개)
```

### 하늘은 **뒤늦게 생깁니다** — 한 번 적용으로는 놓칩니다

처음 넣은 코드는 `SceneLoaded()` 에서 한 번만 하늘에 값을 넘겼습니다.
골프존 실내 모델에서 그게 조용히 실패했습니다.

```
EnvMapBaker.cpp:421   if (proceduralSkyEnabled && m_proceduralSky == nullptr)
                          m_proceduralSky = std::make_shared<SampleProceduralSky>(...);
```

하늘 객체는 **환경맵 경로가 절차적 하늘이 될 때에야** 만들어집니다. 그
모델은 그림자가 꺼진 채로 열려서 태양이 없었고, 태양이 없으면 HDRI 를
씁니다(8-b). 그래서 씬을 읽는 시점에는 `GetProceduralSky()` 가 nullptr 이라
그냥 넘어갔고, 나중에 그림자를 켜자 하늘이 **엔진 기본값 0.75(짙은 구름)**
로 새로 생겼습니다.

화면으로는 못 봤습니다 — 실내라 하늘이 안 보입니다. 절차적 하늘의 **자체
컨트롤 값**을 읽어서 알았습니다: 흐림을 1.00 으로 올렸는데 엔진 쪽은
0.750 그대로였습니다.

고친 방법은 매 프레임 `PushIrisSky()` 를 부르되, **한 번 넣은 하늘 객체는
기억해 두고 건너뛰는** 것입니다. 매 프레임 덮어쓰면 엔진의 Procedural Sky
슬라이더가 먹지 않게 됩니다.

```cpp
const SampleProceduralSky* sky = m_envMapBaker->GetProceduralSky().get();
if (sky == nullptr || sky == m_irisSkyApplied) return;
...
m_irisSkyApplied = sky;
```

고친 뒤 확인 (골프존 실내, 라이브 링크):

| 흐림 | 엔진 cloud density offset |
|---|---|
| 1.00 | **0.000** |
| 0.00 | **1.000** |

### 저장은 손을 뗄 때

ImGui 슬라이더는 **끄는 내내** 바뀜을 돌려줍니다. 그때마다 저장하면 매
프레임 디스크에 씁니다. `m_irisSettingsDirty` 를 세워 두고
`!ImGui::IsAnyItemActive()` 일 때 한 번만 씁니다. 화면 반영은 미루지
않습니다 — 끌면서 보여야 하니까요.

### 라벨은 영어입니다

ImGui 폰트가 `DroidSans-Mono.ttf` 이고 기본 글리프 범위(라틴)로 올라갑니다.
한글을 쓰면 네모로 나옵니다. 설명이 필요한 것은 툴팁으로 붙였습니다.

### 환경변수는 시험용으로 남깁니다

`IRIS_AREA_LIGHTS=0`, `IRIS_IES=0` 은 설정 파일을 건드리지 않고 한 번만
다르게 띄웁니다. A/B 를 잴 때 편합니다.

## 8-i. 유리 — 알파 하나로 정하고 있었습니다 (2026-09-11)

세종 멀티브랜드 모델을 띄우고 "중앙부가 왜 희미한가"를 따라간 결과입니다.

### 무엇이 희미했나

화면 중앙의 큰 매스가 우유빛 막처럼 보였습니다. 광선을 쏴서 확정했습니다
(`iris_alpha_probe.rb` · `iris_glass_probe.rb`):

```
[Translucent Glass Gray]3 · 알파 0.200 · 텍스처 없음
```

우리 규칙은 이것뿐이었습니다:

```cpp
if (sm.alpha < 0.999f && !hasTexture)   // 반투명 + 텍스처 없음
{
    domain             = Transmissive;
    transmissionFactor = 1.0f - sm.alpha;   // 0.8
    roughness          = 0.05f;             // ← 근거 없는 상수
}
```

이름이 `Translucent Glass` 이니 유리로 본 것 자체는 맞습니다. 그런데
**거칠기 0.05 는 연마 판유리**입니다. 이름은 "translucent"(반투명 =
젖빛)인데 거울처럼 매끈한 유리로 그리고 있었습니다.

### 이 모델의 반투명 재질 12개

| 이름 | 알파 | Enscape | 성격 |
|---|---|---|---|
| `Matte__66333`, `_auto_9` | **0.000** | 없음 | SketchUp 에서 **안 보임** |
| `[Translucent Glass Gray]3` | 0.200 | 없음 | 문제의 면 |
| `[Color_004]1`, `C01 색`, `Color_000` | 0.21~0.28 | 없음 | 이름은 **마감 코드** 같지만 차 램프·창입니다(아래) |
| `회색 반투명 유리` | 0.500 | 없음 | 유리 맞음 |
| `Color_A12`, `L16 색`, `Color_A01` | 0.61~0.63 | 없음 | 마찬가지 — `L16 색`은 **미등 렌즈**입니다 |

`Perforated Panel2` 는 **알파 1.0 · 텍스처 있음** — 불투명입니다. 처음에
타공판을 의심했는데 아니었습니다.

**반투명 12개 중 Enscape 설정이 있는 것은 0개입니다.** 전체 98개 중 7개만
Enscape 값이 있고 전부 `GENERIC` 입니다. 즉 이 모델에서는 알파 휴리스틱이
**유일한 근거**입니다.

### 고친 것 셋

#### ① 알파 0 은 안 보이는 것이 맞습니다

SketchUp 에서 알파 0 은 화면에 그려지지 않습니다. 그것을 유리로 바꾸면
프레넬 반사가 남아 **호스트에 없는 것이 보입니다.** 이 모델에 그런 재질이
둘, 201곳 이상에 쓰여 있었습니다.

```cpp
constexpr float kInvisible = 0.002f;
if (alpha <= kInvisible && !authorGlass) { domain = AlphaBlended; opacity = 0; }
```

지오메트리는 지우지 않습니다 — 델타 추적과 재질 상속이 버킷 순서 위에서
돌아갑니다. 재질만 안 보이게 둡니다.

#### ② 저작자의 값이 휴리스틱을 이깁니다

Enscape 는 `Opacity` 와 `IsSolidGlass` 를 남깁니다. 읽고는 있었는데
**쓰지 않고 있었습니다**(10번 검사표 10.2 에 적어 둔 것).

```cpp
const bool authorGlass = ePbr && sm.pbr.solidGlass;
const bool glass       = authorGlass || (alpha < 0.999f && !hasTexture);
```

⚠ **미지정과 '명시적으로 1'을 구별해야 합니다.** `MaterialPbr::opacity` 의
기본값이 1.0 이면, Enscape 설정은 있는데 Opacity 항목이 없는 재질이
"저작자가 불투명이라고 했다"로 읽혀 **SketchUp 의 반투명이 통째로
뒤집힙니다.** 기본값을 음수(미지정)로 바꿨습니다.

이 모델에서는 아무것도 바뀌지 않습니다(Enscape 값이 0개). 포르쉐 모델처럼
Enscape 로 정성껏 만든 모델에서 효과가 납니다.

#### ③ 거칠기를 설정으로 뺐습니다

0.05 는 재고 정한 값이 아닙니다. 커튼월이 맑은 유리인 프로젝트도,
반투명 스크린인 프로젝트도 있습니다. 숨은 상수로 두는 대신 IRIS 패널의
`Glass roughness` 로 뺐습니다 (기본 0.05, 다음 sync 에 적용).

실측 (세종 · 같은 카메라 · 같은 노출):

| 거칠기 | 화면 |
|---|---|
| 0.05 | 우유빛 막 — 뒤가 뭉개집니다 |
| **0.45** | 멀리언 격자와 슬래브가 읽힙니다 |

기본값은 0.05 그대로 둡니다. 한 프로젝트의 입면 하나로 기본값을 바꾸는
것은 **또 다른 근거 없는 상수**일 뿐입니다.

### 통계에 드러냅니다

```
IRIS: 유리로 해석한 머티리얼 9개 (그중 저작자 지정 0) · 안 보임 2 ·
      Enscape 불투명도 적용 0
```

숫자 셋이 각각 ①②③ 이 실제로 걸렸는지를 말해 줍니다. `저작자 지정 0` 은
"이 모델은 휴리스틱으로만 돌고 있다"는 경고이기도 합니다.

### 마감 코드 재질을 따로 봤습니다 — **문제가 아니었습니다**

`C01 색`·`L16 색`·`Color_A01` 처럼 마감 코드 이름을 단 반투명 재질이
유리로 휩쓸린다고 적어 뒀습니다. 무엇에 칠해져 있는지 세어 봤습니다
(`iris_finish_probe.rb`):

```
 # 이름                        알파      면     넓이 m2   어디에
 1 [Translucent Glass Gray]3  0.200      28   2208.36   (루트) — 커튼월
 2 회색 반투명 유리              0.500   19320      6.56   RENAULT KIGER 두 대
 3 Matte__99001               0.500     504      3.12   bagaj · _ncam · door_rf_ok
 4 Color_A12                  0.610     935      2.19   Mesh213 · Mesh15 · …
 5 L16 색                      0.610   10778      0.61   RENAULT KIGER 두 대
 6 Matte__66333               0.000    1189      0.34   farcam
 7 C01 색                      0.240    1074      0.21   stopcam
 8 [Color_004]1               0.210     806      0.19   Mesh119 · Mesh120
 9 Color_A01                  0.630    1130      0.14   Mesh240
10 _auto_9                    0.000    1140      0.04   Mesh229 · Mesh230 · …
11 Color_000                  0.280     174      0.02   Mesh240
```

**건축이 아니라 반입한 자동차 모델 안입니다.** `RENAULT KIGER` 두 대에
다른 차 두 대가 더 있고, 부품 이름이 터키어입니다 — `stopcam`(제동등),
`farcam`(전조등), `_ncam`(앞유리), `bagaj`(트렁크), `door_rf_ok`.
`Matte__66333`·`_auto_9` 같은 이름은 3D 마켓 반출물의 전형입니다.

그리고 **전부 진짜 유리입니다** — 램프 렌즈와 차창입니다. 넓이로 따지면
반투명 면적 2,222 m² 중 커튼월이 2,208 m²(99.4%)이고, 차 네 대의 유리를
다 합쳐도 13.4 m² 입니다.

#### 넓이를 두 번 재야 했습니다 — 첫 숫자는 전부 틀렸습니다

처음 표에는 차창이 585 m², `L16 색`이 54 m² 로 찍혀 있었습니다. 차 두
대에 585 m² 의 유리는 있을 수 없는데 그냥 적었습니다.

원인은 `iris_finish_probe.rb` 의 넓이 계산이었습니다:

```ruby
sc = tr.xaxis.length * tr.yaxis.length     # 틀림
a  = face.area * sc
```

SketchUp 의 `Transformation` 은 **균일 배율을 행렬의 15번째 원소에** 둡니다.
`xaxis` 는 그것과 무관한 축 벡터라 배율이 걸려 있어도 길이가 1 로 나옵니다.
반입 컴포넌트는 거의 항상 그 배율을 쓰므로, 이 식은 배율을 통째로 놓쳤습니다.
`face.area(tr)` 로 바꾸니 숫자가 제자리로 왔습니다:

| | 옛 근사 | 실제 | |
|---|---:|---:|---|
| 회색 반투명 유리 | 585.38 | **6.56** | 89배 부풀림 |
| `L16 색` | 54.28 | **0.61** | 89배 부풀림 |
| `Matte__99001` | 0.18 | **3.12** | 17배 **축소** |

양쪽으로 틀렸다는 점이 중요합니다. 한 방향으로만 틀렸다면 순위는 남았을
텐데, 이 표에서는 **3등과 5등이 뒤바뀌었습니다.**

#### 하마터면 잘못 고칠 뻔했습니다

첫 표를 보고 "큰 면만 유리로 본다"는 규칙이 떠올랐습니다. 커튼월은 100%가
1 m² 이상이고 나머지는 0% 라서 깨끗하게 갈리니까요.

**그 규칙은 램프 렌즈를 깨뜨렸을 것입니다.** `stopcam`·`farcam` 은 작은
면이고 유리가 맞습니다. 데이터가 예쁘게 갈린다고 해서 그 선이 옳은 선은
아닙니다.

#### `L16 색`은 차체가 아니라 **미등 렌즈**였습니다

여기 "39% 투과하는 차체가 남아 있다"고 적어 두었습니다. **틀렸습니다.**

이름(마감 코드처럼 생김)·소유자(`RENAULT KIGER` 바로 아래)·수직면 비율만
보고 차체라고 읽었습니다. 실제로는 **0.61 m² / 10,778면**, 즉 면 하나가
0.57 cm² 인 잔 조각이고, 색은 RGB(102, 28, 26) 짙은 붉은색입니다. 그 두
숫자만 봤어도 차체가 아님을 알 수 있었습니다.

확인 방법은 세는 것이 아니라 **칠해 보는 것**이었습니다
(`iris_body_opaque.rb` 의 `peek`):

```ruby
IRIS::BodyOpaque.peek 5     # 잠깐 자홍색·불투명으로
IRIS::BodyOpaque.unpeek     # 값까지 되돌립니다
```

자홍색은 **미등에 정확히 들어왔습니다.** 같은 방법으로 `Matte__99001` 은
옆 차의 도어 유리, `Color_A12` 는 또 다른 차의 창이었습니다.

> **교훈.** 이름과 통계로는 끝이 안 납니다. 한 번 칠해 보는 데 3초
> 걸립니다. 세 번을 세는 것보다 한 번 보는 편이 쌉니다.

#### 차체는 이미 불투명합니다

반투명(알파 < 0.999) 쪽만 보면 반쪽입니다. **알파는 1.0 인데 IRIS 가
유리로 만들 수 있는** 길이 하나 더 있습니다 — Enscape 의 `IsSolidGlass`
와 `Opacity` 입니다. 재질 98개를 전부 훑었습니다:

```
재질 98개 중 Enscape 설정이 있는 것 7개
알파 1.0 인데 Enscape 때문에 유리가 되는 재질: **없음**
```

즉 이 모델에서 **반투명한 차체는 없습니다.** 고칠 것이 없었습니다.
