# 조명 시스템 (Phase 1 · 4단계)

> 작성일: 2026-09-08

## 1. 전제가 바뀌었습니다

지금까지 문서에 이렇게 적어 왔습니다.

> **SketchUp 에는 광원 엔티티가 없습니다.** 태양과 앰비언트뿐입니다.
> ([04번 7.4절](04-RTXPT-실측.md))

**그건 여전히 사실입니다.** 그런데 실제 프로젝트 모델을 열어 보니 다른 것이
있었습니다.

| 정의 이름 | 인스턴스 |
|---|---|
| `Enscape.SpotLight#1` | 8 |
| `Enscape.SpotLight#2` | 3 |
| `Enscape.SpotLight#3` | 4 |
| `Enscape.SpotLight#4` | 14 |
| **합계** | **29** |

**사용자는 이미 조명을 배치해 두었습니다.** SketchUp 이 광원 엔티티를 주지
않으므로, Enscape 는 **프록시 컴포넌트**로 조명을 표현합니다. 각각 8삼각형짜리
작은 자리표시자이고, 실제 광원 정보는 이름과 (아마도) 속성 사전에 있습니다.

---

## 2. 이것이 왜 중요한가

**기존 Enscape 사용자의 모델이 그대로 켜집니다.**

IRIS 의 경쟁 상대는 Enscape 입니다([02번 문서](02-Enscape-아키텍처-분석.md)).
그 사용자가 IRIS 로 옮기려면 **조명을 전부 다시 배치**해야 한다면, 그것만으로
이주가 막힙니다. 실내 프로젝트 하나에 조명이 수십 개입니다 — 이 모델도 29개입니다.

`Enscape.*` 프록시를 광원으로 해석하면 그 비용이 **0** 이 됩니다.
파일을 열면 조명이 이미 켜져 있습니다.

> 이것은 렌더링 품질이 아니라 **이주 비용**의 문제이고,
> [자료집 0장](01-실시간렌더러-오픈소스-자료집.md)이 말한
> *"제품의 해자는 렌더러가 아니다"* 와 같은 줄기입니다.

---

## 3. 먼저 확인해야 할 것

**속성 사전에 무엇이 들어 있는지 모릅니다.** 그것에 따라 설계가 갈립니다.

| 경우 | 설계 |
|---|---|
| 세기·색·각도가 속성에 있다 | 그대로 읽어 광원을 만든다. 사용자 조작 없이 재현 |
| 이름과 변환행렬뿐이다 | 위치·방향만 얻고 나머지는 IRIS 기본값 + 사용자 조정 |

조사 도구를 만들었습니다:
[`tools/sketchup/iris_lights_probe.rb`](../tools/sketchup/iris_lights_probe.rb)

```ruby
load 'E:/IRIS/tools/sketchup/iris_lights_probe.rb'
IRIS::LightsProbe.run
```

정의 이름·인스턴스 수·**속성 사전 전체**·배치(위치와 Z축 방향)를 찍습니다.
읽기 전용입니다.

## 4. 설계 방향 (조사 결과에 따라 확정)

### 4.1 두 가지 조명 출처

```
① 호스트가 주는 것      태양(그림자 설정), 지오메트리
② IRIS 가 소유하는 것   인공조명

   ②의 초기값을 ①에서 **추출**할 수 있다면 이주 비용이 사라진다
   → Enscape 프록시가 그 경로다
```

### 4.2 프로토콜

`.irisb` 에 `lights` 배열을 추가합니다. 프록시 해석은 **호스트 확장이** 합니다 —
렌더러가 특정 도구의 명명 규칙을 알 필요가 없습니다.

```
Light {
  id:        LightId       // persistent_id
  type:      spot | point | area | directional
  transform: [f64; 16]     // 위치와 방향
  color:     [f32; 3]
  intensity: f32
  cone_deg:  f32?          // 스포트라이트
  source:    string        // "enscape.spotlight" 등 — 출처를 남긴다
}
```

`source` 를 남기는 이유: 사용자가 IRIS 에서 값을 바꿨을 때, 다음 동기화에서
프록시 값으로 덮어쓸지 말지를 판단해야 합니다. **IRIS 에서 손댄 조명은
호스트 값이 이기지 않습니다.**

### 4.3 렌더러

RTXPT 는 `PointLightEx` / `SpotLightEx` 를 이미 갖고 있습니다
(`ExtendedSceneTypeFactory::CreateLeaf`). `SceneBuilder` 가 팩토리에 이름으로
요청하면 됩니다 — 환경광을 만들 때 쓴 것과 같은 방식입니다
([07번 7.3절](07-프로토콜-수신부-설계.md)).

### 4.4 프록시 지오메트리는 렌더하지 않습니다

프록시는 8삼각형짜리 자리표시자입니다. 광원으로 해석했으면 **그 지오메트리는
빼야** 합니다 — 안 그러면 조명 위치마다 작은 상자가 떠 있게 됩니다.

## 5. 남는 질문

| | |
|---|---|
| IES 프로파일 | Enscape 는 IES 파일을 지원합니다. 경로가 속성에 있으면 읽을 수 있고, RTXPT 에도 `IesProfile` 이 있습니다 |
| 태양 | SketchUp 의 그림자 설정(날짜·시각·위치)은 API 로 읽을 수 있습니다. 아직 추출하지 않습니다 |
| 자체 조명 UI | IRIS 에서 조명을 새로 놓고 편집하는 것. 프록시 해석과 별개이며 더 뒤입니다 |
| 발광 재질 | 재질 자체가 빛나는 경우. RTXPT 의 `LightsBaker` 가 처리하지만 SketchUp 재질에는 그 정보가 없습니다 |

## 6. RTXDI 전제를 다시 볼 기회

[04번 4절](04-RTXPT-실측.md)에서 광원을 1 → 1,025 로 늘려도 성능 변화가
**+0.09%** 였고, 자료집 4.1의 *"RTXDI 는 수천~수십만 광원 처리의 핵심"* 이라는
전제와 어긋났습니다.

다만 그 측정은 **합성 씬**이었습니다. 이 모델처럼 **실내에 29개 이상의
인공조명이 있는 실제 씬**이 생기면 제대로 다시 잴 수 있습니다.
4단계가 끝나면 그 측정을 합니다.
