## 1. 전제가 바뀌었습니다

지금까지 문서에 이렇게 적어 왔습니다.

> **SketchUp 에는 광원 엔티티가 없습니다.** 태양과 앰비언트뿐입니다.
> ([04번 7.4절](04-RTXPT-실측.md))

**그건 여전히 사실입니다.** 그런데 실제 프로젝트 모델을 열어 보니 다른 것이
있었습니다. SketchUp 이 광원을 주지 않으므로 Enscape 는 **프록시 컴포넌트**로
조명을 표현하고, 실제 설정은 **속성 사전에 XML 로** 남깁니다.

| 정의 | xsi:type | 인스턴스 |
|---|---|---|
| `Enscape.SpotLight#1`~`#4` | `SketchupIesLight` | 29 |
| `Enscape.PointLight` | `SketchupPointLight` | 18 |
| `Enscape.RectangularLight` | `SketchupRectangularLight` | 4 |
| `Enscape.LinearLight` | `SketchupLinearLight` | 1 |
| **합계** | | **52** |

**사용자는 이미 조명을 배치해 두었습니다.**

> 주의 — 이름에 속지 마십시오. `Ceiling light (Flyingarchs)` 는 인스턴스가 29개라
> 조명처럼 보이지만 **조명기구 모델**입니다. 실제 빛은 그 기구에 칠해진
> **자체발광 재질**에서 나옵니다(5.3절). 판별 기준은 이름이 아니라
> `Enscape.Light` 사전의 유무입니다.

---

## 2. 이것이 왜 중요한가

**기존 Enscape 사용자의 모델이 그대로 켜집니다.**

IRIS 의 경쟁 상대는 Enscape 입니다([02번 문서](02-Enscape-아키텍처-분석.md)).
그 사용자가 IRIS 로 옮기려면 **조명을 전부 다시 배치**해야 한다면, 그것만으로
이주가 막힙니다. 실내 프로젝트 하나에 조명이 수십 개입니다.

프록시를 해석하면 그 비용이 **0** 이 됩니다. 파일을 열면 조명이 이미 켜져 있습니다.

> 이것은 렌더링 품질이 아니라 **이주 비용**의 문제이고,
> [자료집 0장](01-실시간렌더러-오픈소스-자료집.md)이 말한
> *"제품의 해자는 렌더러가 아니다"* 와 같은 줄기입니다.

## 3. 실측한 스키마

`tools/sketchup/iris_dump_attrs.rb` 로 원문을 떴습니다. 조사 도구가 값을 100자에서
자르기 때문에 XML 은 전용 도구가 필요했습니다.

### 3.1 조명 — `Enscape.Light` / `LightData`

```xml
<SketchupLight xsi:type="SketchupIesLight">
  <Luminosity>83860.4024510768</Luminosity>
  <OriginalIesFile>E:\D. 스케치업 자료\ies_data\Bega.8331WIDE.IES</OriginalIesFile>
  <IesData>[base64 로 인코딩된 IES 측광 데이터 전체]</IesData>
</SketchupLight>
```

| 타입 | 필드 |
|---|---|
| `SketchupIesLight` | `Luminosity` · `OriginalIesFile` · `IesData`(base64) |
| `SketchupPointLight` | `Luminosity` · `LightSourceRadius` |
| `SketchupRectangularLight` | `Luminosity` · `Width` · `Length` |
| `SketchupLinearLight` | `Luminosity` · `Length` |

**위치도 방향도 원뿔각도 없습니다.**

- 위치·방향 → 프록시 **인스턴스의 변환**에서 나옵니다. 씬 그래프가 합성하므로
  노드에 광원 잎을 달기만 하면 됩니다. 다만 **어느 축이 정면인지**는 실측해야
  합니다 — 4.2절
- 원뿔각 → **IES 배광**에서 유도합니다(3.3절)
- 색 → 기본값(흰색)이면 아예 적지 않습니다

`Width`·`Length`·`LightSourceRadius` 는 SketchUp 내부 단위인 **인치**입니다
(118.11 인치 = 정확히 3.0 m).

### 3.2 Luminosity 의 단위 — 추론입니다

문서가 아니라 값에서 역추론했습니다. 정직하게 적어 둡니다.

| 광원 | 값 | 루멘으로 읽으면 |
|---|---|---|
| LinearLight | **1000**(정확) | 30 cm 스트립 1000 lm |
| PointLight | 989.28 | 백열 60~75 W 급 |
| RectangularLight | 2831.65 | 3.0 × 2.45 m 패널 |
| IesLight | 83860.4 | 파일 선언 8500 lm 의 9.87배 |

1000 이 정확히 떨어지는 것과 989 lm 이 물리적으로 타당한 것을 근거로
**루멘(lm)** 으로 봅니다. IES 만 크지만, Enscape 의 세기 슬라이더를 올려 잡는 것은
흔한 작업 방식입니다.

틀렸다면 `IRIS::Enscape.lumen_scale` **한 값으로 교정**됩니다.

### 3.3 IES 를 원뿔각으로

RTXPT 는 IES 프로파일을 **아직 지원하지 않습니다.** `LightsBaker.cpp` 에 주석
처리된 예시가 있고 셰이더의 `evaluateIesProfile` 은 비어 있습니다.

그래서 텍스처로 넘기는 대신 배광을 파싱해 원뿔각을 유도합니다 —
50%에서 내부 원뿔(빔각), 10%에서 외부 원뿔(필드각). 조명업계의 정의 그대로입니다.

이 모델의 Bega 8331WIDE 실측:

| | |
|---|---|
| 파일 구조 | 세로각 19 × 가로각 19 = 361 값 · 파싱 후 잔여 0 |
| 유도한 빔각 | 반각 **29.83°** (전각 59.7°) |
| 유도한 필드각 | 반각 **54.25°** (전각 108.5°) — "WIDE" 와 맞습니다 |
| 축상 광도 | 5968.7 cd |
| **구면 적분 광속** | **5088 lm** (선언 램프 광속 8500 lm 대비 효율 59.9%) |

효율 59.9%는 매입 다운라이트의 전형값입니다. **파서가 맞다는 강한 방증**입니다.

> 대칭 배수를 빠뜨리면 안 됩니다. IES 는 대칭이면 일부만 적습니다 —
> 가로각이 0~90 이면 사분 대칭이라 4를 곱해야 전체 광속이 됩니다.
> 빠뜨리면 광속이 4분의 1이 되어 조명이 4배 밝아집니다.

### 3.4 루멘 → 칸델라

Donut 의 `SpotLight::intensity` 는 이름과 달리 **주방향 광도(cd)** 입니다.
셰이더가 `Radiance = flux / d²` 로 쓰고 `getPower() = 4π·flux` 로 계산합니다.

| 종류 | 변환 |
|---|---|
| 점광원 | `I = Φ / 4π` |
| IES 스포트 | `I = Φ × (축상 광도 / 적분 광속)` — **배광을 그대로 보존** |
| 원뿔만 아는 스포트 | `I = Φ / Ω`, `Ω = 2π(1−cos θ)·(1−0.5·softness)` |
| 면광원 | `I = L × A`, 반각 88° 원뿔로 근사 |

세 번째 식은 RTXPT 자신의 `getShapingFluxFactor` 와 같은 근사입니다. 그래야 광원
선택 가중치와 실제 밝기가 어긋나지 않습니다.

**IES 는 근사하지 않습니다.** 배광을 아는데 균일 원뿔로 뭉개면
이 모델에서 **2.37배 어두워집니다**.

## 4. 세 개의 함정 (전부 조용히 틀리는 종류입니다)

### 4.1 `outerAngle` 은 반각입니다

Donut 헤더의 주석은 이렇게 말합니다.

> `float outerAngle = 180.f;` — *Apex angle of the light cone, in degrees*

**RTXPT 는 그렇게 쓰지 않습니다.**

```cpp
// LightsBaker.cpp
polymorphicEx.CosConeAngleAndSoftness = fp32ToFp16(cosf(dm::radians(abs(spot.outerAngle))));
// LightShaping.hlsli
float coneHalfAngle = acos(shaping.cosConeAngle);
```

`cos(outerAngle)` 을 축과의 내적에 직접 비교하므로 **축에서 잰 반각**입니다.
주석대로 전각을 넣으면 원뿔이 두 배로 벌어집니다.

### 4.2 프록시의 정면은 로컬 **+Z** — Donut 과 정반대입니다

Donut 은 glTF 규약대로 로컬 **−Z** 를 정면으로 봅니다.

```cpp
// SceneTypes.cpp
dm::double3 Light::GetDirection() const {
    return -normalize(double3(localToWorld.m_linear.row2));   // 로컬 -Z
}
```

**Enscape 는 +Z 입니다.** 문서에 없으므로 실측했습니다
(`tools/sketchup/iris_lights_axis.rb`).

| 정의 | 로컬 +Z 의 월드 방향 | 아래를 향한 인스턴스 |
|---|---|---|
| `Enscape.SpotLight#2` | (0, 0, −1) | 3 / 3 |
| `Enscape.SpotLight#1` | (0, +0.26, −0.97) | 8 / 8 |
| `Enscape.SpotLight#3` | (0, 0, −1) | 4 / 4 |
| `Enscape.SpotLight#4` | (0, 0, −1) | 28 / 28 |

**43개 전부**입니다. 15° 기울어진 월워셔(`#1`)까지 같은 규약을 따릅니다 —
우연이 아닙니다.

그대로 두었다면 **다운라이트 43개가 전부 천장을 비췄을 것**입니다. 화면은
어두워지지만 오류는 나지 않으므로, 실측하지 않았다면 "조명이 약하다"고
잘못 진단했을 겁니다.

고치는 방법: 광원 잎을 인스턴스 노드에 직접 달지 않고 **X축 180° 회전한 자식
노드**에 답니다. 자식의 −Z 가 부모의 +Z 가 됩니다. 인스턴스 노드의 변환은
건드리지 않습니다 — 그것은 호스트가 보낸 값이고 델타 추적이 그 위에서 돕니다.

> 사각 광원은 애매합니다. 로컬 +Z 가 월드 +Y(수평)를 향합니다. 높이 1.64 m 에
> 4개가 나란히 있으므로 **벽면 패널**로 보는 것이 자연스럽고, 그렇다면 +Z 규약이
> 일관되게 맞습니다. 다만 "그 그룹이 90° 돌아가 있고 실은 아래를 향한다"는
> 해석도 이 데이터만으로는 배제할 수 없습니다. 스포트라이트의 증거를 근거로
> **모든 종류에 +Z 규약**을 적용하고, 화면에서 어색하면 다시 봅니다.

### 4.3 반지름 0인 스포트라이트는 검증되지 않았습니다

```cpp
if (spot.radius == 0.f)
{
    assert(false); // not tested with radius == 0
```

0 이면 `kPoint` 경로로 빠지고 **원뿔 성형이 적용되지 않습니다** — 스포트라이트가
전방위 점광원이 됩니다. 반드시 양수를 줍니다(기본 25 mm).

## 5. 재질 — 같은 발상, 더 큰 효과

### 5.1 스키마 — `Enscape.Material` / `MaterialData`

```xml
<SketchupMaterial Version="5">
  <TypeV5>GENERIC</TypeV5>          <Opacity>1</Opacity>
  <Roughness>0.83</Roughness>       <Metallic>0.109</Metallic>
  <Specular>0.19</Specular>         <IndexOfRefraction>0</IndexOfRefraction>
  <EmissiveColor>#FFFFFF</EmissiveColor>  <EmissiveStrength>5076.7</EmissiveStrength>
  <BumpAmount>2.9999</BumpAmount>   <BumpMapType>BUMP</BumpMapType>
  <NormalMapIntensity>0</NormalMapIntensity>  <IsSolidGlass>false</IsSolidGlass>
  <DiffuseTexture>…</DiffuseTexture>  <BumpTexture>…</BumpTexture>
</SketchupMaterial>
```

**135개 중 26개**에 값이 있습니다. `_sofa fabric` 은 거칠기 0.83 · 금속성 0.109 ·
Specular 0.19 · 범프 3.0 — 설계자가 직접 정한 값입니다.

이것이 *"재질이 섬세하지 않아요"* 에 대한 답입니다. 추측한
`roughness 0.5 / metalness 0` 고정을 **실제 값**으로 바꿉니다.

### 5.2 미결정 B 의 일부가 답을 얻었습니다

[08번 7.4절](08-재질상속.md)에서 세 가지 접근을 두고 미뤄 뒀습니다. 세 번째 —
**Enscape 재질 속성 읽기** — 가 답입니다. 다만 Enscape 모델에만 해당하므로
나머지 109개와, Enscape 를 쓰지 않은 모델은 여전히 미결정 B 입니다.

`Specular` 는 Donut 의 금속-거칠기 모델에 대응 필드가 없어 지금은 **세기만
집계**합니다. 반영 방식은 미결정 B 에서 정합니다.

### 5.3 자체발광 — 천장 조명의 정체

`SELF_ILLUMINATED` 재질 3종의 `EmissiveStrength` 는 3472 · 5077 · 7000 입니다.
**천장 조명 기구 29개는 Enscape 광원이 아니라 이 재질로 빛납니다.**

반영하지 않으면 실내가 어둡습니다. RTXPT 의 `LightsBaker` 는 발광 삼각형을
광원으로 처리하므로 재질에 값만 넣으면 됩니다.

> [08번 6절](08-재질상속.md)에 적어 둔 제약이 여기서 걸립니다 — `LightsBaker` 는
> `geometry->material` 을 봅니다. **인스턴스 덮어쓰기로 넣은 발광은 광원으로
> 잡히지 않습니다.** 이 모델의 발광 재질은 면에 직접 칠해져 있어 문제없습니다.

## 6. 측광 단위와 렌더러 라디언스

Enscape 값은 물리 단위(cd, cd/m²)이고 **렌더러는 그렇지 않습니다.** 환경맵의
하늘이 대략 1.0 인 스케일로 돌아갑니다. 그대로 넣으면 5000배 밝아집니다.

그래서 한 개의 변환 상수를 둡니다 — **1.0 = 5000 cd/m²** (흐린 하늘의 휘도).

| 확인 | |
|---|---|
| 천장 패널 5077 cd/m² | → **1.02** — 하늘과 비슷한 밝기. 맞습니다 |
| 점광원 989 lm, 2 m 거리 | → 벽면 5 cd/m² = 0.001. 실내 조명은 주광보다 훨씬 어둡습니다 |
| IES 스포트, 3 m 거리 | → 2783 cd/m² = 0.56. 밝은 연출 조명 |

절대 밝기는 노출이 흡수합니다. **이 한 값이 지키는 것은 조명끼리·발광
재질끼리의 상대 비율**이고, 그것이 그림의 인상을 정합니다.

`SceneBuilder::SetPhotometricScale` 로 바꿀 수 있습니다. 정식화는 미결정 B.

### 7.0 배선 확인 (2026-09-08)

여섯 단계를 지나가는 동안 어느 한 곳이 필드를 흘리면 **오류 없이 조용히** 조명이
사라집니다. 실제로 `strip_def` 가 떨어뜨릴 뻔했습니다(`d.dup` 이라 살았습니다).

실제 모델 종단 확인:

```
읽기 OK 28.2 ms — 정의 707 · 머티리얼 99 · 뷰 5
구축 OK 497.1 ms — 메시 422 · 지오메트리 546 · 인스턴스 1331 · 삼각형 399916
조명 — 점 18 · 스포트 48 · 총 광속 2,156,588 lm · 발광 재질 6 · Specular 지정 5
```

프로브가 센 **직접 배치 52개**와 렌더러의 **66개**가 다른 것은 정상입니다 —
광원을 담은 그룹 자체가 여러 번 배치되므로 씬 그래프에서 전개됩니다.
지오메트리도 줄었습니다(메시 426→422 · 인스턴스 1360→1331): 프록시가 빠진 것입니다.

합성 씬으로는 **방어 경로**를 고정했습니다. 조명 정의 7개 중 4개만 살아남아야 합니다:

| 정의 | 기대 |
|---|---|
| spot · point · rect | 통과 |
| `badcone` (원뿔 150°) | 반각 범위로 조여서 **살림** |
| `bogus` (종류 불명) | 버림 |
| `negative` (세기 음수) | 버림 |

> 이 시험을 넣다가 **시험 자체의 버그**를 찾았습니다. 오류 경로 시험이
> `good.begin() + 65536` 으로 잘라 왔는데, 36 MB 모델만 쓰는 동안에는 문제가
> 없다가 6 KB 짜리 합성 씬에서 끝을 넘어가 세그폴트로 죽었습니다.
> **시험이 입력 크기를 가정하고 있었습니다.**

### 7.1 프록시 지오메트리는 렌더하지 않습니다

프록시는 광원 자리를 표시하는 컴포넌트입니다. Enscape 도 그리지 않습니다.
그리면 조명 앞에 작은 물체가 떠서 빛을 가립니다.

**프로브 단계에서 뺍니다** — 정의를 만나는 즉시 광원인지 보고, 맞으면 면 추출을
건너뜁니다. 전송량도 줄고 렌더러가 판단할 일도 없습니다.

RTXPT 에는 `LightExtension::Proxies` 로 발광 기구를 광원과 연결해 **이중 계상을
막는** 장치가 따로 있습니다. 우리 프록시는 발광이 아니므로 지금은 쓰지 않지만,
5.3의 발광 기구를 광원과 짝지을 때 쓸 자리입니다.

### 7.2 면광원은 근사입니다

`Rect`·`Linear` 는 발광 지오메트리로 내지 않고 **반각 88° 원뿔 + 등가 면적의
구면 광원**으로 근사합니다. 반각 88°의 실효 입체각이 거의 정확히 π 라서
램버시안 패널의 축상 광도와 맞습니다.

정확한 면광원은 발광 쿼드를 만들어야 하며, 52개 중 5개이므로 뒤로 미룹니다.
